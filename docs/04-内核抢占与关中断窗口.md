## 0. 本篇导读

**一句话结论**：Linux 把"禁止抢占/软中断/硬中断/NMI"四层状态折叠进一个 per-CPU 的 `preempt_count`，抢占模型是**编译期四选一**（NONE/VOLUNTARY/PREEMPT/RT），通用内核的长临界区（spin_lock、非抢占 RCU）只关抢占不关中断；UniProton 用两把独立的"锁"——锁中断（置位 DAIF.I，屏蔽 IRQ）与锁调度（g_uniTaskLock 计数），调度只在两个固定位置发生（任务让出点 + 中断退出尾部），**最坏关中断窗口可静态分析**。

**一个反直觉的事实**：UniProton 在关中断临界区内做的事（如整个内存分配算法）比 Linux 更"重"——但因为这些操作的执行时间是**常数**（见 [06 篇](06-内存管理确定性.md)），关中断窗口依然有界；Linux 虽然把可推迟工作挪到 softirq（只关抢占），但单个 softirq action 的时长没有硬约束（见 [05 篇](05-中断路径确定性.md)）。**"关中断窗口大小"不取决于是否关中断，而取决于临界区内代码的最坏执行时间是否可静态界定。**

## 1. 机制原理

**抢占何时发生**由三个要素决定：检查点在哪、什么条件放行、放行后做什么。

- **Linux**：preempt_count 低 8 位是抢占计数。`preempt_enable()` 时若计数归零且 `TIF_NEED_RESCHED` 置位才调 `preempt_schedule()`。`CONFIG_PREEMPT_NONE` 下 `preempt_enable` **永不触发调度**（include/linux/preempt.h:251-255 的另一编译分支）——这就是"通用内核不可抢占"的代码本体。
- **UniProton**：`g_uniTaskLock`（U16 计数）非零即禁止任务切换。`PRT_TaskUnlock()` 归零时若 `OS_FLG_BGD_ACTIVE` 置位则**立即**触发 `OsTskScheduleFastPs`——解锁即调度，不存在"忘了让出"。

## 2. 架构设计对比

```
Linux preempt_count（一个 32 位字装四层状态）      UniProton 两把独立锁
┌─────────────────────────────────┐          锁中断: DAIF.I 位置 1（PRT_HwiLock）
│ bit31  PREEMPT_NEED_RESCHED(x86)│            → 中断不来，任务照跑
│ 0x00f00000 NMI_MASK  (4bit)     │          锁调度: g_uniTaskLock++（PRT_TaskLock，
│ 0x000f0000 HARDIRQ_MASK(4bit)   │            关中断保护下计数）
│ 0x0000ff00 SOFTIRQ_MASK(8bit)   │            → 中断照来，但中断尾部不切换
│ 0x000000ff PREEMPT_MASK(8bit)   │
└─────────────────────────────────┘          调度只发生在这两处：
  抢占检查点:                                   ① 任务主动让出 OsTskSchedule→OsTaskTrap
  ① preempt_enable 尾部                        ② 中断退出尾部 OsHwiDispatchTail→OsMainSchedule（prt_sched_single.c:146）
  ② 中断返回内核态 irqentry_exit
  ③ 自愿点 cond_resched()                       OsMainSchedule 门卫:
                                                g_uniTaskLock==0 才允许切换
```

## 4. 关键代码路径走读

### 4.1 Linux：preempt_count 的两种编译形态

`include/linux/preempt.h:213-264`：

```c
#define preempt_disable() \
do { preempt_count_inc(); barrier(); } while (0)          /* :213 */

#ifdef CONFIG_PREEMPTION
#define preempt_enable() \
do { barrier(); \
     if (unlikely(preempt_count_dec_and_test())) \
         __preempt_schedule(); } while (0)                 /* :230-235 */
#else
#define preempt_enable() do { barrier(); preempt_count_dec(); } while (0)  /* :251-255 */
#endif
```

`:251-255` 就是"通用内核不可抢占"的代码级证据——`preempt_enable` 只减计数，**永不调用调度器**。

**抢占入口两兄弟**（kernel/sched/core.c）：
- `preempt_schedule()`（:6924）：`preemptible()` 复查（count==0 且开中断）→ `preempt_schedule_common`（:6890）：`do { preempt_disable; __schedule(SM_PREEMPT); } while (need_resched())`
- `preempt_schedule_irq()`（:7039，中断返回内核态）：**先 `local_irq_enable()` 再调度**（:7050）——防止关着中断做长事

**ARM64 特殊性（与 riscv 论述相反：检查留在 arch 入口层）**：6.6 的 arm64 同样没有 x86 式汇编抢占段——entry.S 的向量表（:619）经 kernel_entry（:260）只做现场保存/栈切换，`el1_irq` 汇编符号已随入口重构消失（openEuler-6.6 entry.S 全文 0 处），EL1 中断处理整体在 C 层：`el1h_64_irq_handler → el1_interrupt → __el1_irq`（arch/arm64/kernel/entry-common.c:642-654，:671 调用；:647 irq_enter_rcu、:649 irq_exit_rcu——[05 篇](05-中断路径确定性.md)中断路径的同一锚点）。但与 riscv 把 TIF 检查上交给通用 `irqentry_exit()` 不同，`__el1_irq` 在 `irq_exit_rcu()` 之后显式调用**架构私有**的抢占检查 `arm64_preempt_schedule_irq()`（:651 调用，定义 :295-336）：先过 `need_irq_preemption()`（CONFIG_PREEMPT_DYNAMIC 下是 static key `sk_dynamic_irqentry_exit_cond_resched`，:287-293），再逐一挡掉不可抢占场景——preempt_count 非零（:305，arm64 的 thread_info 打包了 count 与 need_resched）、architected NMI（读 ALLINT，:314）、伪 NMI（GIC 优先级屏蔽下读 DAIF 非零，:323）、cpufeature 未定稿（:334），最后才 `preempt_schedule_irq()`（:335）。即：riscv 是"检查上移到通用 C 层"（irqentry_exit→raw_irqentry_exit_cond_resched，common.c:306-316），arm64 是"检查留在 arch/arm64 入口 C 层"——arm64 自行复刻而非调用通用层（entry-common.c:69 注释直言 "intended to match the logic in irqentry_exit()"），通用层的该检查点在 arm64 的 IRQ 返回路径上并不执行。

> ⚠ openEuler 差异：社区 6.6 中该抢占检查函数名为 `irqentry_exit_cond_resched()`；openEuler-6.6 为配合动态抢占将其拆为 `raw_` 前缀实现 + static_call/static_key 包装（common.c:317-329），调用点在 :357。本文件 openEuler 版仅约 407 行（社区版约 470 行），相关行号已按 openEuler-6.6 实测重定位。

**长临界区实例**：spin_lock 在非 RT 内核 = preempt_disable（include/linux/spinlock_api_smp.h:130-135 的 `__raw_spin_lock` 首句）；非 PREEMPT_RCU 下 `rcu_read_lock()` 直接退化为 preempt_disable（include/linux/rcupdate.h:93-95）——**读临界区最长可占 CPU 的时间没有上界**，这是通用内核经典的非确定源。`PREEMPT_LOCK_OFFSET` 的注释（preempt.h:160）说得很直白："Locks on RT do not disable preemption"。

**动态抢占**：6.6 有 `CONFIG_PREEMPT_DYNAMIC`（kernel/Kconfig.preempt:96-116），启动参数可切 NONE/VOLUNTARY/FULL，arm64 支持（arch/arm64/Kconfig:242 `select HAVE_PREEMPT_DYNAMIC_KEY`），static_key 实现（core.c:6945-6954；arm64 入口层对应 static key `sk_dynamic_irqentry_exit_cond_resched`，entry-common.c:287-293）。

### 4.2 UniProton：锁中断与锁调度

**锁中断** — `PRT_HwiLock()`（src/arch/cpu/armv8/common/hwi/prt_hwi.c:215-225）：

```c
OS_SEC_L0_TEXT uintptr_t PRT_HwiLock(void)          // prt_hwi.c:215
{
    uintptr_t state = 0;
    OS_EMBED_ASM(
        "mrs %0, DAIF      \n"                      // :219 读 DAIF 全文
        "msr DAIFSet, %1   \n"                      // :220 置 I 位 = 屏蔽 IRQ
        : "=r"(state)
        : "i"(DAIF_IRQ_BIT)
        : "memory", "cc");
    return state & INT_MASK;                        // :224 只返回旧 I 位
}
```

语义与 riscv 版等价但**屏蔽方向相反**：riscv **清** mstatus.MIE 才是关中断（读-改-写两个 csr 指令），arm64 **置** DAIF.I 即关中断——且免读-改-写，`msr DAIFSet/DAIFClr` 是 DAIF 的按位置位/清零系统寄存器，立即数用压缩编码：`DAIF_IRQ_BIT = 1U<<1`（src/include/uapi/hw/armv8/os_cpu_armv8.h:34，立即数 bit1 对应 DAIF 的 I），而 DAIF 寄存器里 I 的真实位是 bit7，故返回值掩码 `INT_MASK = 1U<<7`（:37）。保存/恢复语义同样极简：返回旧 I 位，`PRT_HwiRestore`（:230-246）按保存值选择 `DAIFClr`（开中断）或 `DAIFSet`（维持屏蔽）回写——嵌套锁天然正确。

**锁调度（单核版）** — `PRT_TaskLock/Unlock`（src/core/kernel/task/amp/prt_task_minor.c:140-179）：

```c
void PRT_TaskLock(void) {
    uintptr_t intSave = OsIntLock();          // 锁调度必须在关中断下做
    if (g_uniTaskLock == 0) UNI_FLAG &= ~OS_FLG_TSK_REQ;  // 锁住即清调度请求
    OS_TSK_LOCK();                            // g_uniTaskLock++
    OsIntRestore(intSave);
}
void PRT_TaskUnlock(void) {
    uintptr_t intSave = OsIntLock();
    if (g_uniTaskLock == 1) {
        g_uniTaskLock = 0;
        if ((OS_FLG_BGD_ACTIVE & UNI_FLAG) != 0)
            OsTskScheduleFastPs(intSave);     // 解锁即调度！
    } ...
}
```

注意 `:152` 的细节：锁住时**主动清除**调度请求标志——锁调度期间发生的一切唤醒都不积累切换意图，解锁后由下一次中断尾部/后台活动重新评估。SMP 版 `OsTaskIrqUnlock`（smp/prt_task_lock.c:194-219）更精细：归零且 needReschedule 时，若原本关中断只发调度 IPI 不就地调度（避免在他人关中断上下文里切换）。

**中断退出统一调度点** — armv8 把 riscv 版放在汇编尾部的调度判断移进了核心层 C 函数。汇编入口 `OsHwiDispatcher`（src/arch/cpu/armv8/common/hwi/prt_dispatch.S:174）保存通用寄存器与 SPSR_EL1/ELR_EL1 后 `BL OsHwiDispatch`（:191）进 C；从 C 返回即 `b OsContextLoad`（:194）恢复现场、`eret`（:232）——汇编尾部不再做任何判断。判断链在 C 里：`OsHwiDispatch`（prt_hwi.c:182-193，被打断的是任务则保存任务栈指针、切系统栈）→ `OsHwiDispatchHandle`（:130-177）：`OS_INT_COUNT++`（:145）→ 硬件在异常入口同时屏蔽了 IRQ 与 FIQ，先 `OsFiqEnable()`（:148）放行 FIQ → `OsHwiNestedIntEnable`（:156，进入 ISR 前开中断允许嵌套）→ ISR → `OsHwiNestedIntDisable`（:158）→ 清中断号（:165）→ `OS_INT_COUNT--`（:166）→ **仍在嵌套中直接 return（:168-170），只有最外层**调 `OsHwiDispatchTail()`（:176）：

```c
OS_SEC_L0_TEXT void OsHwiDispatchTail(void)        // prt_sched_single.c:118
{
    ...
    do {
        OsIntEnable();                             // :132 执行 tick 前显式开中断
        g_tickDispatcher();
        OsIntDisable();                            // :135
        TICK_NO_RESPOND_CNT--;
    } while (TICK_NO_RESPOND_CNT > 0);             // TICK 补投递（呼应 4.3 第 3 点）
    ...
    OsMainSchedule();                              // :146 非嵌套中断退出必经的统一调度点
}
```

（riscv 版对照 prt_hw.s:211-233：同样的判断留在汇编尾部——`call intterupt_out` 后读 `g_intCount`，非零跳 `intNestRet` 直接恢复现场，归零 `call OsMainSchedule`。语义相同，armv8 把"嵌套判断 + 统一调度"收进 OsHwiDispatchHandle/OsHwiDispatchTail 两个 C 函数。）

`OsMainSchedule`（prt_sched_single.c:55-81）内部由 `OS_FLG_TSK_REQ` 门卫；SMP 版（prt_sched.c:163-195）在 :176 检查 `runQue->uniTaskLock == 0`。任务态入口 `OsTskSchedule`（prt_sched.c:83-99）在 :90 检查硬中断上下文直接 return——**中断里只允许标记，不允许切换**。

### 4.3 UniProton 真实临界区巡礼（三个调用点）

1. **任务睡眠**（PRT_TaskDelay，smp/prt_task_lock.c:103-125）：`OsIntLock` → 校验（中断中/锁中调 Delay 报错）→ `OsSpinLockTaskRq` → `OsTskReadyDel` + 挂超时链 → 解锁 → `OsTskScheduleFastPs(intSave)`。就绪队列操作本身不自带保护，注释明言"调用者确保"（prt_task.c:78-88）。
2. **内存池**（src/mem/prt_mem.c:18-56）：`PRT_MemAlloc/Free` 整个分配算法在 `PRT_HwiLock` 关中断内执行——算法是常数时间（[06 篇](06-内存管理确定性.md)），所以窗口有界。
3. **TICK 补投递**（src/core/kernel/irq/prt_irq_minor.c:108-113）：执行 tick handler 前**显式 `OsIntEnable()`**——内核作者在主动压缩关中断窗口，让 tick 处理可被更高优先级中断打断。

对照 Linux softirq（kernel/softirq.c:535-608）：`handle_softirqs` 在关抢占+**开中断**下跑 action，还有 2ms/10 次重启的软上限兜底——两边都在"缩短关中断"上花心思，但 Linux 用预算机制（时长仍不定），UniProton 用常数时间算法（时长可算）。

> ⚠ openEuler 差异勘误（两库 diff 复核）：`handle_softirqs` 拆分并非 openEuler 特有——社区 6.6.159 同样是 `handle_softirqs`（softirq.c:535-608）+ `__do_softirq()` 薄包装（:610）。softirq.c 的真实 openEuler 差异是新增 `CONFIG_FAST_IRQ` 快速外部中断路径（`xint_enter_rcu`/`__xint_exit_rcu`），详见 [10 篇](10-社区6.6与openEuler6.6调度与核间通信差异.md)。

## 5. 实现差异总结表

| 维度 | Linux 6.6 (arm64) | UniProton (armv8) |
|---|---|---|
| 抢占模型 | 编译期四选一 + PREEMPT_DYNAMIC | 固定：锁调度计数非零即禁切换 |
| 禁调度手段 | preempt_count++（不关中断） | 关中断 + 计数++ |
| 抢占检查点 | preempt_enable 尾/cond_resched/中断返回入口层（arm64_preempt_schedule_irq） | 仅任务让出点 + 中断退出尾部（OsHwiDispatchTail→OsMainSchedule，C 层）两处 |
| 解锁后行为 | 可能调度（NONE 配置下永不） | 归零且有等待需求立即调度 |
| 锁内可否被中断 | preempt_disable 区可被中断打断 | IntLock 区不可；仅锁调度区可（但 OsTskSchedule 拒绝在中断中切换） |
| 最坏关中断窗口 | spin_lock 区不关中断；rcu_read_lock 区时长无上界 | 内存分配全程关中断但算法常数时间；窗口可静态分析 |

**思考题**：

1. Linux `preempt_schedule_irq` 为什么先 `local_irq_enable()` 再 `__schedule`（core.c:7050），而 UniProton `OsTaskIrqUnlock` 在原本关中断时只发 IPI 不就地调度（prt_task_lock.c:202-204）？各自防御什么场景？
