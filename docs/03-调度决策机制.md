# 03 - 技术点1：调度决策机制（固定优先级 O(1) vs EEVDF 公平调度）

## 0. 本篇导读

**一句话结论**：Linux fair 类的决策依据是"资格判定（lag≥0）+ 最早虚截止期"，在 augmented 红黑树上 O(log n) 搜索，追求**按权重公平分享**——代价是单次调度时延随负载浮动；UniProton 的决策依据是"最高优先级就绪任务"，两级位图 + 32 条链表，O(1) 定长扫描，**最坏响应时间可静态推算**。有趣的是：Linux 的 rt 调度类（`rt_prio_array` 位图+链表）与 UniProton 几乎同构——Linux 内部也保留着一个"RTOS 式"调度器，只是被定位为少数实时任务的兜底。

**版本提醒**：openEuler-6.6 基线仍是 Linux 6.6，`fair.c` 是 EEVDF 实现。网上绝大多数教程讲的"旧 CFS：红黑树取最左节点（最小 vruntime）"在 6.6 已不成立，一切以源码为准。另外 6.6 中 `check_preempt_curr()` 已改名为 `wakeup_preempt()`（kernel/sched/core.c:2104），旧函数名 grep 不到（openEuler 的 sched_class 里用 KABI_REPLACE 宏保留旧名做 kABI 兼容，grep 会在 sched.h 命中宏展开字样）。

## 1. 机制原理：决策依据决定时延可预测性

调度器回答一个问题："下一个上 CPU 的是谁？"

- **EEVDF**（Earliest Eligible Virtual Deadline First）的回答：在"有资格"（被欠服务，lag≥0）的任务里，选**虚截止期最早**的。虚截止期 = vruntime + slice×(NICE_0权重/自身权重)。权重由 nice 值决定——高权重任务的虚时间走得慢、截止期更近，于是拿到更多 CPU。这是一个**比例公平**算法：任何时刻的 CPU 份额向权重比收敛，但**单次等待时间没有上界**（新唤醒的高权重任务、负载均衡迁移、资格判定都在改变决策结果）。
- **固定优先级抢占**的回答：位图找最高优先级链表的队首。决策时间是**常数**（不随任务数变化）；一个优先级为 p 的任务的最坏响应时间 = 所有优先级 ≥p 任务的最坏执行时间之和 + 调度延迟——可以用**响应时间分析（RTA）**静态算出。这就是"确定性"的来源，代价是低优先级任务理论上可被饿死。

## 2. 架构设计对比

```
Linux：两级决策（调度类分层 + 类内算法）          UniProton：单级决策
  __schedule()                                     OsTskHighestSet()
    │ for_each_class（按链接地址序）                  │ ① 主位图 clz → 组号
    ▼  stop → dl → rt → fair → ext → idle            │ ② 子位图 clz → 组内优先级
  fair 类内：EEVDF                                    │ ③ 取该优先级链表队首 TCB
    cfs_rq.tasks_timeline (augmented rbtree)          ▼
    按 deadline 排序 + 子树缓存 min_vruntime        g_highestTask（全局缓存）
    pick_eevdf: 资格过滤 + 最小虚截止期搜索
                                                  触发：置 OS_FLG_TSK_REQ 标志
  触发：置 TIF_NEED_RESCHED 标志（惰性）              → 任务上下文立即 OsTaskTrap()
    → schedule()/中断返回点集中 __schedule()          → 中断上下文推迟到中断尾部
```

两者共享同一模式：**触发点只做标记，切换集中在少数出口**。这是好设计的共同点。

## 3. 关键数据结构对比

**L1. 调度类操作表 `struct sched_class`** — `openEuler-6.6/kernel/sched/sched.h:2574-2655`

注意：定义在 kernel/sched/sched.h（不在 include/linux/sched.h）。链接槽位按**链接地址升序 = 调度优先级降序**：`stop → dl → rt → fair → ext → idle`（链接序见 `include/asm-generic/vmlinux.lds.h:129-136`；`for_each_class` 宏 sched.h:2725-2726，`sched_class_above(a,b)` 就是纯指针比较，sched.h:2734）。

> ⚠ openEuler 差异：① sched_class 的多个成员被 KABI_REPLACE/KABI_USE/KABI_EXTEND 宏包裹（openEuler kABI 兼容层），并新增 reweight_task/switching_to/switch_class 等回调；② openEuler 回合了 sched_ext（kernel/sched/ext.c），链接序多出 `__ext_sched_class` 槽位——未启用 CONFIG_SCHED_CLASS_EXT 时该段为空，运行时实际参与调度的仍是 stop/dl/rt/fair/idle 5 个实例。

**L2. EEVDF 四元组（sched_entity）** — `openEuler-6.6/include/linux/sched.h:581-610`

```c
struct sched_entity {
	struct load_weight load;   // :583 权重（nice 决定）
	struct rb_node run_node;   // :584 挂入 cfs_rq->tasks_timeline
	u64 deadline;              // :585 虚拟截止期 vd_i
	u64 min_vruntime;          // :586 子树最小 vruntime（augmented 缓存）
	u64 vruntime;              // :597 虚拟运行时间 ve_i
	s64 vlag;                  // :599 虚拟滞后（正=被欠服务，KABI_BROKEN_REPLACE 内）
	u64 slice;                 // :610 时间片请求长度
};
```

> ⚠ openEuler 差异：sched_entity **没有 min_deadline 字段**（社区 6.6.159 有，本篇原文档曾记录 :556）。openEuler 的 EEVDF 红黑树改为按 deadline 排序、augmented 缓存子树 min_vruntime（见 4.2 ③）；另有 KABI_FILL_HOLE 塞入的 rel_deadline（:590）与 custom_slice（:591，任务自定义 slice 标志）两个标志字节。

**L3. rt 类位图（与 UniProton 对照核心）** — `openEuler-6.6/kernel/sched/sched.h:309-312`

```c
struct rt_prio_array {
	DECLARE_BITMAP(bitmap, MAX_RT_PRIO+1);  // 100+1 位位图
	struct list_head queue[MAX_RT_PRIO];     // 每优先级一条链表
};
```

**U1. UniProton 就绪队列 `struct TagOsRunQue`** — `UniProton/src/core/kernel/include/prt_task_external.h:68-73`

```c
struct TagOsRunQue {
    U32 taskReadyListBitMap;                    // 主位图：每 32 个优先级组占 1 bit
    U32 tskChildBitMap[OS_GET_WORD_NUM_BY_PRIONUM(OS_TSK_NUM_OF_PRIORITIES)]; // 子位图
    struct TagListObject readyList[OS_TSK_NUM_OF_PRIORITIES];  // 每优先级一条双链表
};
```

**位方向的关键设计**（:338, :415-426）：`OS_TSK_PRIO_RDY_BIT = 0x80000000U`，置位宏为 `0x80000000 >> (priority % 32)`——**优先级 0 对应最高位**，前导零计数（clz）扫出的第一个置位位就是最高优先级。全局实例 `g_runQueue`（`src/core/kernel/task/amp/prt_amp_task.c:19`）。

**U2. 任务控制块 `struct TagTskCb`**（同文件 :106-164）关键字段：`priority`（:120 运行优先级，**数字越小越高**）、`origPriority`（:149 原始优先级，PI 用）、`timeSlice`（:154 RR 剩余时间片，cycle 计数）、`pendList`（:160 就绪/等待队列通用节点）。

**优先级参数**：`OS_TSK_PRIORITY_HIGHEST=0 / LOWEST=31 / NUM=32`（`src/core/kernel/task/Kconfig:36-46`）；idle 任务优先级 = LOWEST（`prt_amp_task_init.c:92`）。

## 4. 关键代码路径走读

### 4.1 Linux：__schedule 与选任务

`__schedule()`（kernel/sched/core.c:6617-6745）：`rq_lock`（:6653）→ 读 prev_state（:6667）→ 睡眠则 `deactivate_task` 摘队（:6691）→ `pick_next_task`（:6701）→ `context_switch`（:6739）。

`__pick_next_task()`（core.c:5994-6058）有个重要优化（函数开头 :6000-6001 先查 `scx_enabled()`，sched_ext 启用时直接走 restart 慢路径）：

```c
/* core.c:6009-6012：全系统都是 fair 任务时直通，跳过类循环 */
if (likely(!sched_class_above(prev->sched_class, &fair_sched_class) &&
	   rq->nr_running == rq->cfs.h_nr_running))
	p = pick_next_task_fair(rq, prev, rf);
```

否则 `for_each_active_class(class)`（:6032）从 stop 到 idle 依次询问 `class->pick_next_task(rq, prev)`（:6034）/`class->pick_task(rq)`（:6038）——sched_ext 回合后改用 active 版本并区分两条取任务路径。

### 4.2 Linux fair 类：EEVDF 三步

**① vruntime 更新与到期判定** — `update_curr()`（fair.c:1569-1598）→ `update_deadline()`（fair.c:1365-1388）：

```c
if (vruntime_cmp(se->vruntime, "<", se->deadline))      // :1367 未到期
        return false;
if (!se->custom_slice)                                  // :1375
        se->slice = sysctl_sched_base_slice;
se->deadline = se->vruntime + calc_delta_fair(se->slice, se);  // :1381 vd=ve+r/w
return true;                                            // :1387 到期→交回调用方
// update_curr :1594：if (resched || resched_next_slice(cfs_rq, curr)) resched_curr(rq);
```

> ⚠ openEuler 差异：社区 6.6.159 的 `update_deadline` 返回 void、内部直接 `resched_curr`；openEuler 改为返回 bool，重调度判定挪到 `update_curr`（:1591 先排除 nr_running==1，:1594 增加 openEuler 新增的 `resched_next_slice` 条件）。vruntime 比较也换成本地类型检查宏 `vruntime_cmp`（fair.c:735），并新增 custom_slice 判断（:1375）。

`calc_delta_fair`（fair.c:482-488）：delta ×= NICE_0_LOAD/weight——**权重小 vruntime 走得快**，配额更快耗尽。

**② 资格判定** — `entity_eligible()`（fair.c:1058-1068）：主体一行 `return vruntime_eligible(cfs_rq, se->vruntime);`（:1067；`vruntime_eligible` 在 fair.c:1013，做 `avg_vruntime` 加权平均与自身的比较，本质是 vlag ≥ 0，被欠服务才有资格跑）。openEuler 在函数头部插了 CONFIG_BPF_SCHED 探针（:1060-1065）。

**③ 选任务** — `pick_eevdf()`（fair.c:1253-1328，openEuler 中由 `__pick_eevdf` 改名并增加 `wakeup_preempt` 参数）：在 augmented rbtree 上搜索"合格节点中 deadline 最小"的节点。openEuler 的树按 **deadline 排序**（`entity_before` :800 比较的就是 deadline），augmented 回调 `min_vruntime_cb`（:1160-1161）缓存**子树最小 vruntime**；左子树若 `min_vruntime` 合格则整棵子树都合格、优先递归（:1303-1304）。nr_running==1 时直接返回唯一实体（:1264）。这是 O(log n) 搜索，与旧 CFS"取最左"完全不同。

> ⚠ openEuler 差异：社区 6.6.159 的树按 vruntime 排序、augmented 缓存 min_deadline（本篇原文档如此记录）；openEuler 反转为按 deadline 排序、缓存 min_vruntime（RB_DECLARE_CALLBACKS :1160），且 `pick_eevdf` 带 RUN_TO_PARITY_WAKEUP 保护（:1282，唤醒抢占场景下 curr 的 slice 未用完可跳过资格检查）。

**入队定价** — `place_entity()`（fair.c:5600-5715）：新任务按 lag 补偿定初始 vruntime（保证公平连续性），`deadline = vruntime + vslice`（:5714）。

### 4.3 Linux rt 类：UniProton 的"亲戚"

`pick_next_rt_entity()`（rt.c:1766-1782）：

```c
idx = sched_find_first_bit(array->bitmap);      // :1773 位图找最高优先级
queue = array->queue + idx;
next = list_entry(queue->next, ...);            // :1779 该优先级队首
```

### 4.4 UniProton：一次 O(1) 决策的完整代码

**入队** — `OsTskReadyAdd()`（`src/core/kernel/task/amp/prt_task.c:59-85`）：置 READY → 重置 timeSlice → `OS_TSK_EN_QUE`（底层 `OsEnqueueTaskAmp`，`prt_amp_task_internal.h:53-60`，ListTailAdd FIFO；链表原为空时置主/子位图位，:27-51）→ `OsTskHighestSet()`。

**取最高优先级任务（本篇核心）** — `OsTskHighestSet()`（`src/core/kernel/include/prt_task_external.h:483-500`）：

```c
childBitMapIdx = OsGetLmb1(g_runQueue.taskReadyListBitMap);        // 主位图→组号
rdyListIdx = OsGetLmb1(g_runQueue.tskChildBitMap[childBitMapIdx]); // 子位图→优先级
readyList = &g_runQueue.readyList[(childBitMapIdx << 5) + rdyListIdx];
g_highestTask = GET_TCB_PEND(OS_LIST_FIRST(readyList));            // 队首 TCB
```

`OsGetLmb1`（`src/utility/lib/prt_lib_math64.c:58-71`）是**软件循环模拟 clz**（`for(i=31;i>=0;i--)` 找最高置位）——不是硬件 CLZ 指令，但循环上界固定 32 次，仍是 O(1) 语义。两级位图的意义：优先级数扩展到 N 时，主位图把扫描范围从 N/32 次降到 1+1 次。

**调度触发（标志位模式）** — `OsTskSchedule()`（`prt_amp_task.c:24-40`）：

```c
OsTskHighestSet();
if ((g_highestTask != RUNNING_TASK) && (g_uniTaskLock == 0)) {
    UNI_FLAG |= OS_FLG_TSK_REQ;           // 只做标记
    if (OS_INT_INACTIVE) OsTaskTrap();    // 任务上下文：立即切换
}                                        // 中断上下文：推迟到中断尾部
```

**决策生效** — `OsMainSchedule()`（`src/core/kernel/sched/prt_sched_single.c:55-81`）：检查 `OS_FLG_TSK_REQ` → 换 `RUNNING_TASK = g_highestTask` → `OsTskContextLoad()` 恢复上下文（不再返回）。中断侧的统一出口在 `OsHwiDispatchTail`（`src/core/kernel/irq/prt_irq_minor.c:118-127`）。

**tick 唤醒** — `OsTaskScan()`（`prt_amp_task.c:79-124`）：扫**有序**延时链（按到期 tick 排序，`OsTskTimerAdd`，prt_task.c:90-113），`expirationTick > g_uniTicks` 即 break（不用全扫）；到期任务按状态清位、`OsTskReadyAddBgd` 入就绪队列，最后 `OsTskScheduleFast()`。

**同优先级 RR（可选）** — `OsHwiEndCheckTimeSlice()`（`prt_sched_single.c:21-48`）：非 RR 任务直接 return；时间片耗尽则 `OsTskReadyDel` + `OsTskReadyAdd` 重挂队尾。时间片是**物理 cycle**（`g_timeSliceCycle = 时钟频率×timeSliceMs`，prt_task_init.c:49），与 Linux 的"虚时间片"（按权重缩放）语义完全不同。整套 RR 依赖编译选项 `OS_OPTION_RR_SCHED`（hi3093 参考配置实测**未启用**：`build/uniproton_config/config_armv8_hi3093/defconfig:189`）。

## 5. 实现差异总结表

| 维度 | Linux 6.6 fair (EEVDF) | Linux 6.6 rt | UniProton |
|---|---|---|---|
| 决策依据 | 资格(lag≥0)+最早虚截止期 | 纯优先级数值 | 纯优先级数值 |
| 队列结构 | 1 棵 augmented rbtree | 100 位位图+100 链表 | 主位图+子位图+32 链表 |
| 找最高任务 | 树搜索 O(log n) | find_first_bit+队首 O(1) | 两次 OsGetLmb1+队首，O(1) |
| 时间片语义 | slice→虚截止期（按权重缩放） | 无 | 物理 cycle；到期同优先级轮转 |
| 时延上界 | 无静态上界（负载相关） | 有（rt_prio 域内） | 有（可 RTA 推算） |
| 公平性 | 比例公平（EEVDF 理论保证） | 无（FIFO/RR within prio） | 无（同优先级 FIFO/RR） |
| 调度锁 | preempt_count/rq lock | 同左 | g_uniTaskLock 计数 |

## 6. 代码阅读指导

**推荐路线**（先 UniProton 后 Linux，由简入繁）：

1. `UniProton/src/core/kernel/include/prt_task_external.h:68`（TagOsRunQue）→ `:483`（OsTskHighestSet）→ `src/utility/lib/prt_lib_math64.c:58`（OsGetLmb1）——先看懂"一张位图"的 O(1) 决策
2. `UniProton/src/core/kernel/task/amp/prt_task.c:59`（ReadyAdd/Del）→ `prt_amp_task.c:24`（OsTskSchedule 置标志）→ `prt_sched_single.c:55`（OsMainSchedule 生效）→ `irq/prt_irq_minor.c:118`（中断出口收口）
3. `openEuler-6.6/kernel/sched/sched.h:2574`（sched_class）→ `core.c:5994`（__pick_next_task）→ `core.c:6617`（__schedule）
4. `openEuler-6.6/kernel/sched/rt.c:1766` + `sched.h:309`——与 UniProton 对照：你会看到几乎相同的位图+链表结构
5. `openEuler-6.6/kernel/sched/fair.c:1569`（update_curr）→ `:1365`（update_deadline）→ `:1058`（entity_eligible）→ `:1253`（pick_eevdf，openEuler 改名）→ `:5601`（place_entity）

**实验建议**：Linux 侧写两个不同 nice 值的 CPU 密集线程跑 10s，`time` 对比用户时间比例是否接近权重比（1.25:1 per nice step）；再写一个 SCHED_FIFO 线程与 CFS 线程同跑，观察 FIFO 是否始终先跑。

**思考题**：

1. UniProton 把优先级 0 放位图最高位（0x80000000 右移），Linux rt 位图用 find_first_bit 从最低位找——两种位方向各换来什么？若 UniProton 换成硬件 `clz`（AArch64 基础指令集自带 CLZ），哪段代码可删？
2. Linux"置 TIF_NEED_RESCHED 延迟到 __schedule 才切换"与 UniProton"置 OS_FLG_TSK_REQ 后立即 OsTaskTrap"——在多核场景（远端 CPU 有更高优先级任务就绪）下，两者的实现代价差异是什么？（提示：`resched_curr` 的 `smp_send_reschedule` IPI，core.c:1114-1115）
3. 同优先级两任务：Linux fair 用虚截止期谁先到谁先跑，UniProton 用固定 cycle 时间片轮转队尾。若两任务 nice 不同，两套机制各自如何保证公平？`vlag` 在其中起什么作用？
