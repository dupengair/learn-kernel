## 0. 本篇导读

**一句话结论**：Linux 的 PI 实现在 rt_mutex——每锁一棵按优先级排序的红黑树 + 每任务一棵"等待我的任务"PI 树，阻塞时沿锁链**逐级传播**优先级并做**死锁环检测**（约 1800 行核心 + 1234 行 futex PI）；UniProton 的 PI 只在互斥信号量上（编译开关 + 二进制型 + PRIOR 模式三重前提）——阻塞时 `OsPriorityInherit()` 就地沿链提升 owner，释放时反向扫描持有集取最高 pend 优先级回退（约 500 行）。**但请注意边界事实**：Linux 通用（非 PREEMPT_RT）内核的普通 mutex **没有 PI**（FIFO 唤醒，mutex.c:943），优先级反转在通用内核依然存在——PI 不是"通用内核 vs RTOS"的差异，而是"Linux 内部给实时路径的特殊能力 vs RTOS 的必选项"。

**版本提醒**：6.6 中 `rt_mutex_waiter_is_higher()` 已重构为 `rt_waiter_node_less()` + `rt_mutex_steal()`（rtmutex.c:371/407）；UniProton 的设计文档 doc/design/sem.md 通篇未提"优先级继承"——PI 只存在于 uapi 注释与代码里（prt_sem.h:297），这是"文档滞后于代码"的活例子。

> ⚠ openEuler 差异：本篇 Linux 侧参考 openEuler-6.6（OLK-6.6，基线 6.6 + openEuler 补丁集）。kernel/locking/rtmutex.c、rtmutex_common.h 与 kernel/futex/ 全部锚点与社区 6.6 一致，PI 链实现无 openEuler 特有改动；kernel/sched/core.c、include/linux/sched.h、kernel/locking/mutex.c 因 openEuler 调度相关补丁行号整体后移（rt_mutex_setprio 7067→7123、sched.h PI 字段 1149→1204、mutex.c FIFO 唤醒 937→943）。

## 1. 机制原理

**优先级反转场景**（开场必讲）：低优先级任务 L 持有互斥锁 M → 高优先级任务 H 阻塞在 M 上 → 中优先级任务 N（不碰 M）抢占 L → H 被 N "间接"阻塞，实际等待时间取决于 N——与设计优先级相悖。

**PI 协议**：H 阻塞时把 L 临时提升到 H 的优先级（L 尽快跑完临界区）；L 释放时回退。难点在**链式传播**（L 又阻塞在 N' 持有的锁上）与**死锁环**（A 等 B、B 等 A）。两边的解法深度不同：

- Linux：显式建链（task->pi_blocked_on）+ 显式环检测 + 链长上限 1024
- UniProton：就地 while 循环沿链提升，靠"owner 优先级不再更低"自然终止，无显式环检测

## 2. 架构设计对比

```
Linux rt_mutex PI                              UniProton 互斥信号量 PI
 H 阻塞在锁M                                  H 阻塞在互斥信号量S
  waiter 进两棵树:                              H 按优先级插入 S->semList
   ├ M->waiters (rbtree, 受wait_lock保护)       OsPriorityInherit():
   └ L->pi_waiters (rbtree, 受pi_lock保护)       owner = S->semOwner
 L->priority ← H.prio (rt_mutex_setprio)         while (owner.prio > newPrio)
 L 也阻塞? → pi_blocked_on 指向其 waiter            owner.prio = newPrio
  → rt_mutex_adjust_prio_chain:                     owner 就绪队列同步搬移
    13步锁序协议, 每步≤2把锁                        owner 也阻塞?
    环检测: lock==orig → -EDEADLK                    ├ 是: 沿 taskPend→semOwner
    链长上限: 1024                                   │   下一跳必须是 SEM_TYPE_BIN
 释放: mark_wakeup_next_waiter                      └ 非互斥型: 链断终止★无环检测
  先 deboost 再把锁"留给"top waiter               释放: OsSemPendListGet
  丢锁后才 wake_up_q                              ├ semOwner 过户给队首任务★
                                                  └ OsPriorityRestore:
                                                    以 origPriority 为底
                                                    扫 semBList×semList 取最高
```

**UniProton 的双链设计**值得注意：`sem->semList`（谁在等这把锁）+ `task->semBList`（我持有哪些互斥锁）——恢复优先级时反向扫描用。

## 3. 关键数据结构

**L1. `struct rt_mutex_base`** — linux include/linux/rtmutex.h:23-27：`wait_lock` + `waiters`（rb_root_cached，leftmost 即 top waiter）+ `owner`（指针 bit0 复用为"有等待者"标志，状态表见 rtmutex.c:65-90 注释）。

**L2. `struct rt_mutex_waiter`** — linux kernel/locking/rtmutex_common.h:32-59：**一个 waiter 进两棵树**（`tree` 挂锁等待树 / `pi_tree` 挂 owner 的 PI 树，两份排序键因锁序不同而独立）；排序键 `prio` + `deadline`（DL 任务按截止期）。

**L3. task_struct 的 PI 字段** — linux include/linux/sched.h:1204-1211：`pi_waiters`（等待我的所有 waiter）/ `pi_top_task` / `pi_blocked_on`（我阻塞在哪个 waiter 上——链式走读的"下一跳"）。

**L4. 普通 mutex（反例）** — linux include/linux/mutex.h:66-79：`wait_list` 是 **list_head FIFO**，无优先级树无 PI。:132-174 的 `#else /* !CONFIG_PREEMPT_RT */` 分支下 mutex 整体替换为 rtmutex——**PI 是 PREEMPT_RT 的能力，不是通用内核的**。

**U1. `struct TagSemCb`** — UniProton src/core/ipc/include/prt_sem_external.h:87-118：

```c
struct TagSemCb {
    U32 semCount;                  // 计数器
    struct TagListObject semList;  // 阻塞队列（PRIOR 模式按优先级有序）
    struct TagListObject semBList; // 挂到持有任务上：任务→持有互斥锁集合
    U32 semOwner;                  // 持有者 PID（互斥型有效）
    enum SemMode semMode;          // FIFO / PRIOR
    U32 semType;                   // 低4位=COUNT/BIN，高位=protocol(PI位)
};
```

**U2. TCB 关键字段** — UniProton src/core/kernel/include/prt_task_external.h:119-164：`priority`（:120 运行优先级）/ `origPriority`（:149 原始优先级，恢复依据）/ `taskPend`（:140 我阻塞在谁上）/ `pendList` / `semBList`。

**U3. 模式与开关**：`PRT_SemMutexCreate` 固定 `SEM_TYPE_BIN + SEM_MODE_PRIOR`（prt_sem_init.c:184-188）；PI 编译开关 `OS_OPTION_SEM_PRIO_INHERIT`（实证 build/uniproton_config/config_armv8_hi3095/defconfig:55-59，注释 "SEM_PRIO_INHERIT depend on SEM_PRIOR and BIN_SEM"）。

## 4. 关键代码路径走读

### 4.1 Linux：rt_mutex PI 三部曲

**① 阻塞入队 + 首跳提升** — `task_blocks_on_rt_mutex()`（rtmutex.c:1180-1280）：自死锁早退（:1205 `-EDEADLK`）→ waiter 双树入队 → 若是新 top waiter：更新 owner 的 PI 树并直接 `rt_mutex_adjust_prio()`（:1242-1246）→ owner 自己也阻塞则发起链走（:1274）。

**② 链式传播（精华）** — `rt_mutex_adjust_prio_chain()`（rtmutex.c:655-1051）：先读 :603-651 的大注释——13 步锁序协议（[R]引用计数/[P]pi_lock/[L]wait_lock，每步至多持两把锁、全程可抢占）。关键点：

```c
if (++depth > max_lock_depth) return -EDEADLK;      // :681 链长上限1024
if (lock == orig_lock || rt_mutex_owner(lock) == top_task)
        ret = -EDEADLK;                              // :837 ★显式死锁环检测
...
if (waiter == rt_mutex_top_waiter(lock)) {           // :969-979 重排队后提升
        rt_mutex_dequeue_pi(task, ...);
        waiter_clone_prio(waiter, task);
        rt_mutex_enqueue_pi(task, waiter);
        rt_mutex_adjust_prio(lock, task);
}
next_lock = task_blocked_on_lock(task);              // :1014 链推进
```

**③ 提升落地到调度器** — `rt_mutex_setprio()`（kernel/sched/core.c:7123-7240）：改 `pi_top_task` → dequeue/re-enqueue（boost 到队头 ENQUEUE_HEAD，:7214）→ `check_class_changed` 触发抢占判断——**这就是"提升后立刻可能抢占"的联动点**。

**④ 释放** — `mark_wakeup_next_waiter()`（rtmutex.c:1288-1334）：

```c
waiter = rt_mutex_top_waiter(lock);              // 唤醒最高优先者，非 FIFO
rt_mutex_dequeue_pi(current, waiter);
rt_mutex_adjust_prio(lock, current);             // 先降权再交锁
lock->owner = (void *)RT_MUTEX_HAS_WAITERS;      // 锁"留给"top waiter，防低优先 steal
```

:1321-1330 注释解释为何 deboost 与 wakeup 之间要 preempt_disable（窗口期自身反转）。用户态可用 PI：FUTEX_LOCK_PI → kernel/futex/pi.c:930（栈上 rt_waiter 走代理锁）。

### 4.2 UniProton：互斥信号量 PI 全链

**① 阻塞入队（按优先级插队）** — `OsSemPendListPut()`（prt_sem.c:240-282）：先出就绪队列、置 PEND → PRIOR 模式下 `LIST_FOR_EACH` 找到第一个优先级更低的任务插它前面（同优先级 FIFO）→ **立刻** `OsPriorityInherit(semPended, runTsk)`（:278-281）。

**② 就地链式提升（核心）** — `OsPriorityInherit()`（prt_sem.c:153-198）：

```c
semOwnerTask = GET_TCB_HANDLE(semPended->semOwner);
while (semOwnerTask->priority > newPriority) {       // 数值大=优先级低才需提
    if (TSK_STATUS_TST(semOwnerTask, OS_TSK_READY)) {
        OsTskReadyDel(semOwnerTask);                 // 就绪队列同步搬移
        semOwnerTask->priority = newPriority;        // 只改运行值，origPriority 不动
        OsTskReadyAdd(semOwnerTask);
    }
    recurSem = (struct TagSemCb *)semOwnerTask->taskPend;  // owner 也阻塞?
    if (GET_SEM_TYPE(recurSem->semType) != SEM_TYPE_BIN) return;  // 非互斥型: 链断★
    semOwnerTask = GET_TCB_HANDLE(recurSem->semOwner);      // 沿链上一级
}
```

注意链断条件：下一跳必须还是互斥型信号量。**没有环检测**——A↔B 互等场景靠 while 条件隐式收敛（环上优先级提到相同值后条件不成立），是否为有意设计可作为讨论点。

**③ 释放：过户 + 恢复** — `PRT_SemPost`（prt_sem.c:485-508）→ `OsSemPendListGet`（:287-323）：取 semList 首个（最高优先任务）入就绪队列，**直接把 semOwner 过户给它**（:310，对照 Linux 的"锁留给 top waiter"手法）→ `OsPriorityRestore()`（:203-234）：以 `origPriority` 为底，遍历自己 semBList 上每把互斥锁的 semList 队首取最高 pend 优先级（`OsGetPendTskMaxPriority`，:69-85），降级重挂就绪队列 → `OsTskSchedule()` 显式触发调度（给被让权者立刻抢占的机会）。

**④ 使用约束（PI 状态机的代价）** — `OsCheckPrioritySet`（prt_sem.c:90-123）：优先级被继承期间（origPriority != priority）**禁止** `PRT_TaskSetPriority`。

**⑤ 其他 IPC 无 PI 的反例**：队列纯 FIFO（src/core/ipc/queue/prt_queue.c:75 `ListTailAdd` 队尾追加，doc/design/queue.md:16 "先进先出"）；事件是标志位语义无 owner 概念（prt_event.c）；计数信号量固定 FIFO 模式（prt_sem_init.c:176）且 `OsPriorityInherit :159-161` 对非 BIN 型直接 return。

## 5. 实现差异总结表

| 维度 | Linux 6.6 rt_mutex PI | UniProton 互斥信号量 PI |
|---|---|---|
| 适用范围 | rtmutex 家族、PREEMPT_RT 下 mutex/spinlock/rwlock、futex PI（用户态） | 仅二进制互斥信号量 + 三重前提（编译开关+BIN+PRIOR）；计数信号量/队列/事件均无 |
| 等待队列 | 每锁一棵 rbtree（缓存 top waiter），RT/DL 双键排序 | 每信号量一条链表，插入时线性找位 |
| 优先级记录 | waiter 双树双键；task 侧 pi_waiters/pi_top_task | TCB 双字段 priority/origPriority；恢复时反向扫描 |
| 传播链 | adjust_prio_chain：13 步锁序、可抢占、可重试 | OsPriorityInherit 就地 while，全程持锁/关中断 |
| 死锁环处理 | 显式检测 -EDEADLK + 链长上限 1024 | 无显式检测，while 条件隐式收敛 |
| 释放语义 | 先 deboost 再把锁留给 top waiter（防 steal） | 唤醒队首并直接过户 semOwner，随后恢复 |
| 调度联动 | rt_mutex_setprio→re-enqueue→check_class_changed | 改 priority 同步搬就绪队列，Post 后显式 OsTskSchedule |
| 使用约束 | 对用户透明 | 被继承期间禁改优先级；中断禁 pend |

## 6. 代码阅读指导

**推荐路线**：

1. `openEuler-6.6/include/linux/rtmutex.h:23`（锁三字段）→ `kernel/locking/rtmutex_common.h:32`（waiter 双树双键）
2. `openEuler-6.6/kernel/locking/rtmutex.c:65`（owner 编码状态表）→ `:371,407`（排序与 steal）→ `:1180`（task_blocks_on_rt_mutex）
3. `openEuler-6.6/kernel/locking/rtmutex.c:603-1051`（**先读大注释再读函数体**：adjust_prio_chain）
4. `openEuler-6.6/kernel/sched/core.c:7123`（提升落进调度器）→ `rtmutex.c:1288,1387`（释放两段）
5. `openEuler-6.6/include/linux/mutex.h:36,132`（两个编译分支）+ `kernel/locking/mutex.c:943`（FIFO 唤醒——"通用内核为何没 PI"的证据）
6. `openEuler-6.6/kernel/futex/syscalls.c:146` → `kernel/futex/pi.c:930,613,1101`（用户态 PI 全链）
7. `UniProton/src/include/uapi/prt_sem.h:243,297`（模式枚举与 PI 承诺）→ `src/core/ipc/include/prt_sem_external.h:87`（TagSemCb 双链）
8. `UniProton/src/core/ipc/sem/prt_sem.c` 按调用序通读：`:240`（入队）→ `:153`（继承）→ `:287`（唤醒过户）→ `:203`（恢复）→ `:366`（Pend）→ `:458`（Post）
9. `UniProton/src/core/ipc/queue/prt_queue.c:41-85`（FIFO 反例）+ `testsuites/kern-test/sem_mutex_test.c:115-159`（**现成的 PI 实验**：test_prior_inherit_task_A/B/C 三任务演示反转与恢复）

**思考题**：

1. Linux"先 deboost 再唤醒"并在其间 preempt_disable（rtmutex.c:1321-1330）；UniProton"先过户再恢复"（prt_sem.c:310-322）。两者都在防什么竞争？顺序颠倒分别会发生什么？
2. UniProton 继承链遇到 owner 阻塞在**计数型**信号量时链断（prt_sem.c:185-191），Linux 的 adjust_prio_chain 无论下一跳锁类型都继续走。对"A（持互斥锁 M）阻塞在计数信号量 S，S 的消费者优先级低于被 M 阻塞的 H"场景，两种设计的后果差异是什么？
3. 通用 Linux mutex 为何长期"不修"优先级反转？从使用模型（内核任务多 SCHED_OTHER、临界区短、有 optimistic spinning osq）与代价（每任务 PI 树维护）两方面论证；再对比 UniProton 作为 RTOS 为什么必须把 PI 做进互斥信号量。
