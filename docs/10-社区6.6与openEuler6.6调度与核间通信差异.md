## 0. 本篇导读

**写作背景**：本工作区 Linux 侧参考代码从社区 linux-6.6.159 切换为 openEuler-6.6（OLK-6.6 分支）后，02~09 篇教案已按 openEuler-6.6 重测行号。当时 6.6.159 目录已删除，"社区版形态"只能靠文档记录推断，产生过三处归因错误（见 §5 勘误）。现在两个源码树并存于本地，本文用**逐文件 diff + git log** 给出调度与核间通信两个方向的差异全貌——既是差异清单，也是"对比学习时哪些结论可跨版本迁移、哪些不能"的依据。

**一句话结论**：openEuler-6.6 与社区 6.6.159 在**机制主干上高度一致**（rtmutex PI 全链、futex、preempt.h、rpmsg 总线、virtio 三表、IPI 路径逐行相同），差异集中在三处——**调度子系统整体回移了 mainline 6.9~6.12 的演进**（sched_ext、EEVDF 树结构反转）、**KABI 二进制兼容保护**（约 117 处宏）、**openEuler/华为自研特性**（FAST_IRQ、cgroup IFS、SCHED_SOFT_QUOTA、CCA 机密计算、LIVEPATCH_WO_FTRACE）。

## 1. openEuler-6.6 是什么

- openEuler OLK-6.6 分支源码（git 仓库，`Makefile` SUBLEVEL=0 + `Makefile.oever` 定义 OPENEULER_LTS/MAJOR/MINOR），openEuler 24.03 LTS 等发行版使用的内核分支，持续吸收 CVE 修复与特性。
- 构成可以理解为四层叠加：
  1. **6.6 stable 早期基线**（非 6.6.159 终点——见 §3.2 remoteproc 反例，openEuler 错过了部分后期 stable 重构）；
  2. **mainline 前瞻特性回移**：sched_ext（mainline 6.11，git 铁证 `26b33e66b8c8 sched_ext: Implement BPF extensible scheduler class`）、EEVDF 修复系列（6.12）、entry 框架重构（6.12）等；
  3. **openEuler/华为自研**：CONFIG_FAST_IRQ、cgroup IFS 干扰统计、CONFIG_SCHED_SOFT_QUOTA、可靠内存、virtcca/hisi CCA 机密计算、LIVEPATCH_WO_FTRACE；
  4. **KABI 保护**：sched.h 60 处 + include/linux/sched.h 57 处 KABI 宏，`sched_entity`/`sched_class`/`task_struct` 字段用 KABI_BROKEN_REPLACE/KABI_USE/KABI_FILL_HOLE 包裹（社区内核无此层）。
- 因此它**不是** 6.6.159 的超集或子集：6.6.159 有 remoteproc resource 解析重构而 openEuler 没有；openEuler 有 sched_ext 而 6.6.159 没有。两者是**分叉后各自演进**的关系。

## 3. 重点差异详解

### 3.1 调度：sched_ext 整体回移（差异最大的一块）

openEuler-6.6 把 mainline 6.11 的 **sched_ext（BPF 可编程调度类）** 完整搬了进来（`kernel/sched/ext.c`，6.6.159 无此文件）。连带效应遍布调度框架：

- **链接序从 5 槽变 6 槽**：`vmlinux.lds.h` 新增 `*(__ext_sched_class)`，调度类优先序变为 `stop → dl → rt → fair → ext → idle`。不启用 `CONFIG_SCHED_CLASS_EXT` 时运行时仍等效 5 类，但 lds 槽位无条件保留（阅读 03 篇 sched_class 链接序结论时以此为准）。
- **调度类接口演进**（为 scx 服务，各调度类同步改）：
  - `dequeue_task_*` 返回 `void → bool`（如 rt.c:1546、fair.c:8008 `static bool dequeue_task_fair`；6.6.159 分别为 void/void）；
  - `put_prev_task_*(rq, prev, next)` 增加 `next` 参数（openEuler fair.c:10706；6.6.159 无此参数）；
  - `__pick_next_task` 开头新增 `scx_enabled()` 快捷检查（core.c:6000），类循环改 `for_each_active_class`，并区分 `pick_next_task`/`pick_task` 双路径；
  - 6.6.159 的 rt.c 里独立 `pick_next_task_rt()` 在 openEuler 中已并入通用选任务逻辑。
- **KABI 包裹**：`struct sched_class` 成员被 KABI_REPLACE/KABI_USE/KABI_EXTEND 包裹并新增 `reweight_task`/`switching_to`/`switch_class` 等回调——读 openEuler 源码时看到这些宏不是调度逻辑，是发行版兼容层。

**对学习的影响**：03 篇"调度类分层 + 链接地址定优先级"的框架结论不变，但 openEuler 版多一个 ext 层可玩——BPF 写调度策略与 UniProton"编译期固定调度器"是很好的对照题。

### 3.2 调度：EEVDF 树结构反转（影响 03 篇口径的实质差异）

这是 fair 类**算法级**差异，源自 mainline 6.12 的 EEVDF 修复系列回移：

| 维度 | 社区 6.6.159 | openEuler-6.6 |
|---|---|---|
| 红黑树排序键 | **vruntime** | **deadline**（反转） |
| augmented 缓存 | 子树 `min_deadline`（`__update_min_deadline`，fair.c:807-819） | 子树 `min_vruntime`（`RB_DECLARE_CALLBACKS`，fair.c:1160） |
| 选任务入口 | `__pick_eevdf`（:881）+ 包装 `pick_eevdf`（:975） | 单一 `pick_eevdf(cfs_rq, wakeup_preempt)`（:1253，带唤醒场景参数） |
| sched_entity 字段 | 有 `min_deadline`（include/linux/sched.h:556） | **删除**，KABI_FILL_HOLE 塞入 `rel_deadline`(:590)/`custom_slice`(:591) |
| 到期重调度 | `update_deadline` 返回 void、内部 `resched_curr` | 返回 **bool**，判定挪到 `update_curr`（:1594，并新增 openEuler 自研的 `resched_next_slice` 条件） |
| 其他 | — | nr_running==1 快路径（:1264）、RUN_TO_PARITY_WAKEUP 保护（:1282）、`vruntime_cmp` 本地宏（:735） |

资格判定（lag≥0）与"虚截止期最早"的 EEVDF 基本思想两版一致，**变的是数据结构布局与查找方向**——03 篇已按 openEuler 形态更新并在文中加了 ⚠ 注。读旧教程/旧资料对照 6.6.159 时注意此分叉。

### 3.3 调度：openEuler 自研特性（三处值得单独研究）

1. **CONFIG_FAST_IRQ**（kernel/softirq.c，48 行差异的全部内容）：新增 `xint_enter_rcu()`/`__xint_exit_rcu()` 快速外部中断进出路径，绕过部分 irq_enter 记账（受 `CONFIG_DEBUG_FEATURE_BYPASS` 控制）——压缩硬中断进入开销的实时优化方向，与 UniProton"中断路径固定化"思想可对照。
2. **cgroup IFS 干扰统计**（include/linux/cgroup.h:903-911，kernel/locking/mutex.c:26 处差异的主要构成）：mutex 慢路径埋点 `cgroup_ifs_enter_lock(&ifs_clock)` / `cgroup_ifs_leave_lock(ifs_clock, IFS_MUTEX)`，统计锁类干扰时间——这也是 08 篇 mutex.c FIFO 唤醒 937→943 行号偏移的来源。rtmutex.c **未**埋此点（PI 链零差异）。
3. **CONFIG_SCHED_SOFT_QUOTA**（fair.c:194、idle.c:484、features.h:141）：fair 类配额干预，6.6.159 无此配置项。
4. （关联 07 篇）**CONFIG_LIVEPATCH_WO_FTRACE**（arch/riscv/kernel/traps.c:270-285 `klp_breakpoint_handler`）：免 ftrace 的热补丁断点方案，导致 `do_trap_ecall_u` 308→331 后移——与调度无关但修正了 07 篇的一处归因（见 §5）。

### 3.4 核间通信：virtio_ring.c 的 CCA 机密计算适配（+18 行）

差异全部是地址处理（kick 路径外围）：

```c
if (virtcca_cvm_domain()) return true;              // 华为 CCA 机密虚机域
#ifdef CONFIG_HISI_CCADA_GUEST
    if (is_realm_world()) return true;              // Realm 世界（CCADA）
#endif
#ifdef CONFIG_HISI_CCA
    addr = dma_addr_canonical(addr);                // CCA 场景还原规范地址
#endif
```

影响：`virtqueue_kick_prepare` 2345→2363、`virtqueue_kick` 2390→2408（09 篇已按此更新）。**vring 三表 UAPI（virtio_ring.h）零差异**——描述符表/可用环/已用环的机制分析在两版间完全可迁移。

### 3.5 核间通信：remoteproc_core.c——openEuler 反而是旧形态（107 行）

方向性差异，值得注意：6.6.159 包含 stable 后期的 resource table 解析重构（`rproc_rsc_cb_data` + 回调式 `rproc_handle_rsc_entry`），而 **openEuler-6.6 保留 v6.6 原始的 for 循环逐项解析（`rproc_handle_resources`）**——openEuler 基线早于该重构进入 stable 的时间点，且没有回移它。

影响：`rproc_fw_boot` 1371→1382 等行号偏移（09 篇已更新）。对 09 篇的生命周期走读（fw_boot → 搬段 → start → notify）无语义影响，两条路径做的事一致。

### 3.6 零差异区（跨版本可迁移的结论）

以下在本系列教案中大量引用、且**两版逐行一致**，所有对照结论可直接跨版本迁移：

- `include/linux/preempt.h` —— preempt_count 位段、四种抢占编译形态、PREEMPT_LOCK_OFFSET（04 篇全部引用行号在两版相同）
- `kernel/locking/rtmutex.c`、`rtmutex_common.h` —— PI 链全部锚点（owner 编码 :65、`rt_waiter_node_less` :371、`rt_mutex_steal` :407、`adjust_prio_chain` :603-1051、`task_blocks_on_rt_mutex` :1180、释放 :1288/:1387）（08 篇核心）
- `kernel/futex/pi.c`、`futex/syscalls.c` —— 用户态 PI 全链一致
- `arch/riscv/kernel/entry.S`、`arch/riscv/mm/context.c`、`include/asm/ptrace.h` —— 上下文切换 14 寄存器、satp/sfence.vma 路径（07 篇核心）
- `drivers/rpmsg/virtio_rpmsg_bus.c`（1081 行）、`rpmsg_ns.c`、`remoteproc_virtio.c`、`imx-mailbox.c`、`virtio_ring.h` —— rpmsg 名字空间、vring 通知、mailbox 打铃（09 篇核心）
- `kernel/smp.c`、`arch/riscv/kernel/smp.c` —— IPI 收发（resched_curr 的 `smp_send_reschedule` 路径）

## 5. 勘误记录（单侧推断 → 双侧 diff 的教训）

切换基线时 6.6.159 目录曾被删除，当时靠"原文档记录 + openEuler 单侧实测"推断社区版形态，产生了三处归因错误，本次双侧 diff 后已就地修正（04/05/07 篇内"勘误"注）：

1. `handle_softirqs` 拆分：曾标注为"openEuler 差异"，实际 **6.6.159 同样有**（softirq.c:535 主体 + :610 薄包装，两版行号都一样）；真差异是 CONFIG_FAST_IRQ。
2. `__trap_section` 标记：曾标注为"openEuler 回移 6.10"，实际 **6.6.159 同样有**（traps.c:130 定义、:308 使用）；真差异是 LIVEPATCH_WO_FTRACE。
3. `should_fail_futex`：曾写"openEuler 多出的故障注入"，实际 **6.6.159 同样有**（futex/syscalls.c:201），两侧该函数逐行一致。

根因：这些特性都在 6.6.y stable 生命周期内合入（或在原始基线已存在），而"社区版形态"的想象来自更早的 v6.6 tag。**教训：归因必须双侧实测，`diff` 是唯一可信的依据。**

## 6. 代码阅读指导

```bash
cd /home/dupengair/shared/kernel/learn-kernel
# 任一文件的两侧差异（本文数字即此命令统计）
diff linux-6.6.159/kernel/sched/fair.c openEuler-6.6/kernel/sched/fair.c | grep -c "^[<>]"
# 追溯 openEuler 侧某差异的来源 commit（判断回移还是自研）
git -C openEuler-6.6 log --oneline --format="%h %s" -- kernel/sched/ext.c | tail -3
# 例：26b33e66b8c8 sched_ext: Implement BPF extensible scheduler class
```

推荐路线：

1. **看调度差异全貌**：`diff -u linux-6.6.159/kernel/sched/rt.c openEuler-6.6/kernel/sched/rt.c`（55 行，最小可完整读懂的 sched_ext 接口适配样本：dequeue bool、put_prev next 参数、pushable 迭代）
2. **看 EEVDF 反转**：两侧分别读 `__pick_eevdf`（6.6.159 fair.c:881）与 `pick_eevdf`（openEuler fair.c:1253），对照 `RB_DECLARE_CALLBACKS`（:1160）理解排序键互换
3. **看自研实时特性**：openEuler kernel/softirq.c 的 `xint_enter_rcu`；include/linux/cgroup.h:903-911 的 IFS 结构
4. **验证零差异结论**：`diff linux-6.6.159/kernel/locking/rtmutex.c openEuler-6.6/kernel/locking/rtmutex.c`（应无输出）
5. **核间通信**：`diff -u` virtio_ring.c 的 18 行（CCA 适配）与 remoteproc_core.c 的 107 行（新旧 resource 解析形态对照——同一段逻辑的两种写法，本身是好的重构教材）

**思考题**：

1. sched_ext（BPF 可编程调度类）与 UniProton 编译期固定的调度器，分别把"调度策略的可变性"放在哪一层？对实时系统的 WCET 分析各意味着什么？
2. openEuler 给 mutex 慢路径埋 IFS 干扰统计点、却不在 rtmutex.c（PI 链）埋——从"观测开销 vs 路径确定性"角度分析这样选择的合理性。
3. EEVDF 排序键从 vruntime 反转为 deadline 后，为什么 augmented 缓存也要跟着从 min_deadline 换成 min_vruntime？（提示：缓存的是"另一维"的聚合值，服务于剪枝方向。）
