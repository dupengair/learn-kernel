## 0. 本篇导读

**一句话结论**：Linux 是"单体内核 + 两态隔离 + 系统调用"的独立 ELF；UniProton 是"静态库内核 + 单态裸机 + 函数直调"的单一 ELF。后续所有篇章的差异（无陷入开销、无地址空间切换、无缺页）都由这个形态差异派生。

本篇回答三个问题：
1. "内核"这两个字在两边分别指什么实体？
2. 从上电到第一个用户执行体，两边各走什么路径？
3. 应用调一个 API，两边各经过什么环节？

## 1. 机制原理：形态为什么决定实时性

**API 路径长度 = 实时性的第一道门槛。**

- Linux 应用调用 `write()`：glibc 包装 → `svc #0` 特权指令陷入 EL1 → `kernel_entry` 宏全量寄存器压栈（pt_regs，336 字节）→ 查 `sys_call_table[]` 间接跳转 → 进入/退出安全框架检查（ptrace/seccomp/audit/TIF 标志循环）→ `eret` 返回。每次调用固定承担这套开销。
- UniProton 应用调用 `PRT_TaskDelay()`：一条 `bl` 指令。API 与应用同特权级（EL1）、同 ELF、同地址空间，**没有"进内核"这个动作**。

第二层含义是**加载与生命周期**：Linux 内核是独立 vmlinux，常驻内存、先于所有用户进程启动；UniProton 内核编译成 `.a` 静态库（`libHI3093.a`），与应用目标文件链接进同一个镜像——"启动内核"和"启动程序"是同一件事。

第三层含义是 **ABI 形态**：Linux 系统调用号是稳定的 ABI（只能尾部追加），调用号本身是接口标识；UniProton 的 `PRT_*` 接口没有编号，只有函数签名，接口存在性由**链接期**决定（符号缺失即 `undefined reference`），运行期不存在"未实现的调用"。

## 2. 架构设计对比

```
Linux（两态）                          UniProton（单态）
┌─────────────────────────┐            ┌──────────────────────────────┐
│  用户态 (EL0)            │            │        单一 ELF @0x93000000   │
│  app + glibc             │            │  ┌────────────────────────┐  │
│    │ syscall(SYS_write)  │            │  │ app (openamp/main.c)   │  │
│    ▼ svc #0 ─────────┐  │            │  ├────────────────────────┤  │
│ ═══════ 特权边界 ════│══│            │  │ litelibc (pthread 直调) │  │
│  内核态 (EL1)         ▼  │            │  ├────────────────────────┤  │
│  vectors → el0_svc      │            │  │ UniProton 内核(静态库)   │  │
│  → sys_call_table       │            │  │ sched/mem/irq/ipc...    │  │
│  → __arm64_sys_write    │            │  │ 同一 .text 段，无隔离    │  │
│  独立 vmlinux，页表隔离  │            │  └────────────────────────┘  │
└─────────────────────────┘            └──────────────────────────────┘
启动终点: exec /sbin/init               启动终点: OsFirstTimeSwitch 永不返回
```

## 3. 关键证据（数据结构 / 链接脚本）

**E1. Linux 系统调用分发表** — `openEuler-6.6/arch/arm64/kernel/sys.c:58-61`

```c
const syscall_fn_t sys_call_table[__NR_syscalls] = {
	[0 ... __NR_syscalls - 1] = __arm64_sys_ni_syscall,   // 默认项=未实现（本体 sys.c:41-44）
#include <asm/unistd.h>                                  // 宏展开逐项覆盖（__SYSCALL 双宏 :51-56）
};
```

- 调用号从 x8 寄存器取：`do_el0_svc()` 读 `regs->regs[8]`（`arch/arm64/kernel/syscall.c:190`）；查表前先做 `scno < sc_nr` 上界检查，再经 `array_index_nospec()` 掩码索引（`syscall.c:49-52`），越界号不查表、直接 `do_ni_syscall()`（`syscall.c:22-34、54`）。表项签名统一为 `long (*)(const struct pt_regs *)`（`syscall_fn_t`），`SYSCALL_DEFINE` 生成的 `__arm64_sys_*` 包装从 pt_regs 拆参；`el0_svc_common()` 同时把号码回写 `regs->syscallno`（:82）供 ptrace 读取（`arch/arm64/include/asm/syscall.h:24-27`）
- 未实现调用的兜底：`sys_ni_syscall()` 返回 `-ENOSYS`（`kernel/sys_ni.c:20-23`）；arm64 表内默认项是其包装 `__arm64_sys_ni_syscall`（`arch/arm64/kernel/sys.c:41-44`）
- 编号即 ABI 的证据：6.6 最新调用仍按序追加在尾部（`include/uapi/asm-generic/unistd.h:820-824`，`__NR_cachestat 451`、`__NR_fchmodat2 452`）；`arch/arm64/include/uapi/asm/unistd.h:38` 直接 `#include <asm-generic/unistd.h>`——arm64 没有专属调用号表，编号完全复用 generic 序列，uapi 头只负责挑选 `__ARCH_WANT_*` 旧接口开关（:31-36）

> ⚠ openEuler 差异：`include/uapi/asm-generic/unistd.h` 在社区 6.6 基线（453 map_shadow_stack 封顶）之后继续尾部追加了 openEuler 自有调用号——`__NR_vstream_manage 454`（:829-830）、`__NR_kabi_reserved455~466`（KABI 预留槽，全部指向 `sys_ni_syscall`，:832-855）、`__NR_xsched_setattr/getattr 467/468`（openEuler 调度增强，:856-859），`__NR_syscalls` 由社区 6.6 的 454 扩到 469（:861-862）。追加方式仍是"只在尾部加号"，本身即是 ABI 只增不改策略的又一例证。

**E2. UniProton API：纯 C 函数声明，无调用号** — `UniProton/src/include/uapi/prt_task.h:1165`

```c
extern U32 PRT_TaskCreate(TskHandle *taskPid, struct TskInitParam *initParam);
```

**E3. 单一 ELF 的链接脚本** — `UniProton/demos/hi3093/build/hi3093.ld:6-37`

```
MEMORY { IMU_SRAM (rwx) : ORIGIN = 0x93000000, LENGTH = 0x800000
         MMU_MEM  (rwx) : ORIGIN = 0x93800000, LENGTH = 0x800000 }
ENTRY(__text_start)
.text : { *(.text) *(.text.*) *(*.text) ... } > IMU_SRAM
```

`.text` 通配吞并所有目标文件的代码段——内核函数与应用函数落在**同一段**。ARM64 demo 额外开了 MMU（`bsp/mmu.c` 建 `g_mem_map_info[]` 页表），但所有映射区 `.virt == .phys` 恒等映射，仅用于区分内存属性（代码段 RX、外设 Device-nGnRnE），不做地址空间隔离——"单一地址空间"的形态在 A 核上不变；页表本身也放在镜像内（hi3093.ld 的 `.mmu.table.base` 段）。

**E4. 静态库链接证据** — `UniProton/demos/hi3093/CMakeLists.txt:19-20,62-70,121`

- 编译选项 `-march=armv8.2-a -nostdlib -nostdinc -nostartfiles`（裸机，:19-20）
- `link_libraries(... libs/libHI3093.a ...)`（:66）—— 内核以静态库参与链接，同链还有 libmetal.a/libopen_amp.a（:68-70）
- `add_executable(${APP} ${OBJS})`（:121 等各 APP 分支）—— bsp+config+app 的目标对象合成一个可执行文件

**E5. pthread 适配 = 直调内核** — `UniProton/src/libc/litelibc/src/thread/pthread_create.c:166-231`

`__pthread_create` 内部直接调 `OsTaskCreateChkAndGetTcb()`、`OsTskContextInit()`、`PRT_TaskResume()`（:193/:207/:220）——pthread 与内核任务之间没有陷入边界，只是包了一层函数。（注意：`src/kal/` 目录在本仓库只有 IPC 适配，POSIX 线程适配实际位于 `src/libc/litelibc`。）

## 4. 启动路径走读

### 4.1 Linux：start_kernel 到第一个用户进程

| 步 | 函数 | 位置 | 要点 |
|---|---|---|---|
| 1 | `start_kernel()` | init/main.c:855 | C 入口，0 号进程上下文 |
| 2 | `setup_arch()` | init/main.c:878 | 早期初始化、DTB 解析 |
| 3 | `mm_core_init()` | init/main.c:913 | 建内存分配器（**6.6 已由 mm_init 改名**，旧资料勿用） |
| 4 | `sched_init()` | init/main.c:925 | 调度器初始化（中断未开） |
| 5 | `rest_init()` | init/main.c:665-712 | `user_mode_thread(kernel_init)` 诞**生 1 号进程**（:676）；`kernel_thread(kthreadd)` 诞生 2 号（:689）；0 号退化为 idle（:711） |
| 6 | `kernel_init()` | init/main.c:1417-1490 | 释放 initmem 后 `try_to_run_init_process("/sbin/init")`（:1482 起）**exec 第一个用户态进程**，失败则 panic |

此后每次 `write()` 都是一次完整陷入（详见 [07 篇](07-API路径与上下文切换开销.md)）。

### 4.2 UniProton：0x93000000 到第一个用户任务

| 步 | 函数 | 位置 | 要点 |
|---|---|---|---|
| 1 | `OsElxState` | demos/hi3093/bsp/start.S:40-96 | 读 `CurrentEL` 判断启动异常级；EL2 起步则配 `HCR_EL2` 后 `ERET` 降级到 **EL1h**（:82-96） |
| 2 | `Start` | start.S:98-113 | 设 `sp = __os_sys_sp_end`（:107）、`BL mmu_init` 恒等映射（:110）、`B OsResetVector`（:113） |
| 3 | `OsResetVector` | src/arch/cpu/armv8/common/hwi/prt_reset_vector.S:40-43 | `LDR x0,=OsVectorTable; MSR VBAR_EL1,X0` 设异常向量基址；清寄存器/BSS 后 `BL main`（:155） |
| 4 | `main()` | demos/hi3093/apps/openamp/main.c:522-524 | 仅一句 `return OsConfigStart();` |
| 5 | `OsConfigStart()` | demos/hi3093/config/prt_config.c:501-528 | `OsHwInit()`（:512，空函数）→ `OsRegister()`（:515）→ `OsInitialize()`（:521）→ `OsStart()`（:527） |
| 6 | `g_moduleConfigTab[]` 扫描 | prt_config.c:255-305 | SYS/MEM/HWI/TSK/TICK…/**APP→PRT_AppInit**（:289），模块化注册-初始化 |
| 7 | `PRT_AppInit()` | main.c:437-496 | `RpmsgHwiInit()` 注册核间中断（:455）；`OsTestInit()` 创建第一个用户任务 "TestTask"：优先级 25、栈 0x3000 |
| 8 | `OsActivate()` | src/core/kernel/task/amp/prt_task_init.c:139-159 | 创建 IdleTask（优先级 31 = LOWEST）→ `OsFirstTimeSwitch()`（:156）**永不返回** |
| 9 | `OsTskEntry()` | prt_task_init.c:164-185 | 所有任务统一入口：取 TCB → 调 `taskEntry` → `OsTaskExit` |

**关键洞察**：UniProton 的 `main()` 不是被调度的任务——它跑在一个"优先级 LOWEST+1 的伪任务"上下文里（`prt_amp_task_init.c:73`，比空闲任务还低），只负责把内核拉起来；`OsFirstTimeSwitch()`（`prt_sched_single.c:101-113`，注释 "never get here"）之后控制权永久交给调度器。对照 Linux：0 号进程退化 idle 后仍常驻调度——差别在于 Linux 需要 idle 兜底循环，UniProton 的 IdleTask 接过了这个角色。ARM64 上另有两处与 riscv64virt 不同：异常向量基址由内核汇编 `OsResetVector` 写 `VBAR_EL1`（`prt_reset_vector.S:42-43`，不再是应用责任），且入口先从 EL2 降级到 EL1（`start.S:82-96`）——裸机 RTOS 也必须处理 AArch64 的异常级拓扑，但降级后全程单一 EL1，"单态"结论不变。

## 5. 实现差异总结表

| 维度 | Linux 6.6（ARM64, EL1） | UniProton（hi3093, EL1） |
|---|---|---|
| 内核形态 | 单体内核，独立 vmlinux | 静态库 libHI3093.a + 应用合成单 ELF |
| API 路径 | glibc → svc #0 → vectors/el0_svc → sys_call_table → 内核函数 | 普通 bl 指令直调 |
| API 标识 | 系统调用号（x8），ABI 稳定只增不改 | 函数符号，无编号 |
| 未实现 API | sys_ni_syscall → -ENOSYS（运行期） | 链接期 undefined reference |
| 入口/终点 | start_kernel → exec /sbin/init | OsElxState → OsResetVector → main → OsFirstTimeSwitch 永不返回 |
| 首个用户执行体 | init 进程（用户态 EL0） | "TestTask" 任务（优先级 25） |
| 内存布局 | 内核/用户地址空间页表隔离 | IMU_SRAM 0x93000000 单一映像（MMU 恒等映射仅管属性），.text 不分内核/应用 |

## 答疑区

### Q1：UniProton 像 MCU 裸机程序吗？多个应用怎么跑？这种应用跟 Linux 上写 .out 有什么差异？

**Q1-a：是不是"应用直接跑在裸金属上"，类似 MCU 裸机程序？**

**形态上"像"，本质上"不像"——应用不是直接跑在金属上，而是跑在一个 RTOS 内核之上。**

先说"像"的三点（都是本篇已证的事实）：

1. **单地址空间，无任务级虚拟内存**：hi3093 虽然开了 MMU，但全部恒等映射（`.virt == .phys`），只用来区分内存属性（代码 RX/外设 Device），不做地址空间隔离——没有每任务页表、没有缺页、没有按需换页。
2. **单特权级，无用户态/内核态**：任务与内核同在 EL1（任务 SPSR 初值 0x305 = EL1h），`PRT_TaskDelay()` 就是一条 `bl` 指令，没有"进内核"这个动作。
3. **内核 = 静态库**：`libHI3093.a` 与应用链接成同一个 ELF，没有独立的内核实体。

但**与 MCU 裸机程序（bare-metal）有本质区别**：裸机程序是 `main` 里 `while(1)` 死循环 + 中断打断，"并发"只有中断这一种；UniProton 应用之上有一个完整的 RTOS 内核在运行——调度器（优先级抢占）、GIC 中断管理、TICK、IPC（信号量/队列/事件）、FSC 内存分区。应用代码是被**调度器调度执行的任务**，不是独占 CPU 的主循环。你在裸机上手工写的"主循环状态机 + 标志位"，在 UniProton 里被拆成多个任务由内核代管。

还有一个容易混淆的点：**形态相似，成因不同**。Cortex-M（armv7-m）是硬件本来就没有 MMU/特权级扩展，单一形态是被迫的；UniProton 在 A 核（armv8）上是**主动关闭** MMU 地址空间与 EL0 用户态——硬件有而不用，换取确定性（任务切换零地址空间动作、最坏时延可静态分析，见 [07 篇](07-API路径与上下文切换开销.md)）。UniProton 本身也跨这两类核（`build.py` 同时支持 m4 与 hi3093 这类 A 核），同一套 RTOS 把 MCU 形态带上了 A 核。

**Q1-b：一个核上跑多个应用怎么跑？与写 Linux .out 的差异？**

先纠正一个概念：**UniProton 里没有"多个应用"这个单位，只有"多个任务"**。所谓多个应用，就是一个镜像里的多个任务组。hi3093 demo 的实证（`demos/hi3093/apps/openamp/main.c`）：`PRT_AppInit`（:437-496）一口气创建了 `masterLogTask`（优先级 24）、`TestTask`（25）、`DriverSampleEntry`（26）、`SlaveTaskEntry`（:252-255 等多处 `PRT_TaskCreate`）——它们共享同一个 `.text`、同一个地址空间，由调度器按优先级抢占分时跑在一个核上。

任务通过 `struct TskInitParam`（`src/include/uapi/prt_task.h:1111-1130`）定义——7 个字段就是应用的全部"进程控制块"：

```c
struct TskInitParam {
    TskEntryFunc taskEntry;    // 入口函数（替代 Linux 的 main）
    TskPrior taskPrio;         // 静态优先级 0-31（数字越小越高，替代调度器的动态决策）
    uintptr_t args[4];         // 传参（最多 4 个指针）
    U32 stackSize;             // 栈大小（静态预算，不会按需增长）
    char *name;
    uintptr_t stackAddr;       // 栈地址：0=系统从 FSC 堆分配，非 0=用户指定
    U16 policy;                // 调度策略（FIFO/RR，RR 需编译开关）
};
```

写法上的核心转变：**`main` 不是应用主体，只是引导**（本篇 4.2 已述——`OsFirstTimeSwitch` 后 main 被永久抛弃）。应用的真正主体是任务函数，惯例是"初始化 + 循环"体，且循环里必须有让出点。看 demo 真实任务（main.c:151 起 `TestTaskEntry`）：

```c
void TestTaskEntry()
{
    TestOpenamp();                          // 一次性初始化
    ...
    while (!is_tty_ready()) {
        PRT_TaskDelay(OS_TICK_PER_SECOND / 10);   // ★轮询 + Delay 让出 CPU
    }
    ...
}
```

与 Linux 写 .out 的逐项差异：

| 维度 | Linux `.out`（进程） | UniProton（任务） |
|---|---|---|
| 入口 | `main()` 即应用 | `main` 只做引导创建任务；`taskEntry` 才是应用 |
| 执行单位 | 进程（资源分配）+ 线程（调度） | 只有任务（执行与资源一体） |
| 地址空间 | 每进程独立页表，MMU 隔离 | 全部任务共享一张恒等映射页表 |
| 野指针后果 | 段错误，死自己（内核回收） | 踩别人内存，**死整个系统**（无保护） |
| API 路径 | syscall 陷入（svc #0） | `bl` 直调 `PRT_*`（无陷入） |
| 阻塞方式 | 库/内核帮你阻塞（read/futex 睡眠） | 必须主动让出：`PRT_TaskDelay`/信号量 Pend/队列收发；**不让出的死循环会饿死同优先级及以下的任务**（高优先级仍能抢占） |
| 生命周期 | 运行期 fork/exec 动态加载 | **链接期静态决定**，没有运行期加载（形态篇的"链接期 undefined reference"） |
| 栈 | 按需增长（缺页扩栈） | 创建时定死 `stackSize`，溢出靠水位检查（`topOfStack`）事后发现 |
| libc | 完整 glibc/musl | litelibc POSIX 子集（malloc/stdio/pthread 有，pthread 直调内核任务） |
| 多应用通信 | 管道/socket/共享内存（有内核中转或协商） | PRT 信号量/队列/事件，或直接读写共享内存（同一地址空间，天然共享） |
| 并发单位开销 | 进程 mm/页表/fd 表，重 | 一个 TCB + 一块静态栈，极轻（创建时间是常数，见 [06 篇](06-内存管理确定性.md)） |

一句话概括：**写 UniProton 应用 ≈ 写一个"单地址空间、静态链接、直调 API、必须自律让出 CPU"的多线程程序**——它像 Linux 里的"多个线程"（共享内存、调度单位）胜过像"多个进程"；又像 MCU 的"主循环拆分"（静态、无动态加载），但每个循环体被内核赋予了优先级和栈。收益是行为可静态分析（几个任务、多少栈、什么优先级，链接后即确定）；代价是失去了进程隔离这把保护伞——可靠性从"MMU 兜底"变成"代码自律 + 静态审查"。

补充：还有一种"多个应用"的形态——**跨核**。MICA 混合部署下 Linux 跑一部分核、UniProton 跑另一部分核，两边的"应用"通过 rpmsg 通信（见 [09 篇](09-MICA混合部署与核间通信.md)）。那是用物理核隔离替代地址空间隔离的另一个极端。

### Q2：能像 Linux 那样跑多个 ELF 吗？把几个 Linux 应用移植过来，是不是基本要重写？

**Q2-a：能跑多个 ELF 吗？**

**默认形态不能**——UniProton 没有 exec/fork（litelibc 无对应实现源文件），镜像在链接期定死，"多应用"只能以"链接期合并 + 多任务"存在（Q1-b）。但源码里有**两个例外口子**，语义都与 Linux 跑 ELF 不同，需要认清：

1. **动态模块 dlopen（可选组件，唯一的运行期加载代码的口子）**。`dlopen()`（`src/libc/litelibc/src/ldso/dlopen.c:3-5`）直调 `OsDynModuleLoad()`（`src/core/extend/dlmodule/prt_dynmodule.c:480`）：`stat`/`open`/`read` 从**文件系统**读一个 ELF（:77-94）→ 检查 Ehdr → 分配内存、重定位加载段与符号表 → `dlsym()`（dlsym.c:3-5 → `OsDynModuleFind`）取函数指针调用。由 `CONFIG_OS_OPTION_DYNAMIC_MODULE` 控制（ascend310b/sd3403/x86_64 的 defconfig:169 开启；hi3093 未开），且实现依赖 SMP（prt_dynmodule.c:31）与文件系统挂载。
   **关键定性：这是插件语义，不是进程语义。** 加载进来的 ELF 没有自己的 main、没有独立地址空间、没有独立调度身份——它只是被现有任务 `dlsym` 后调用的"一段可卸载代码"，等价于 Linux 的 `.so` 插件，而不是 `.out` 进程。用途是"不停机扩展功能"（如协议解析插件），不是"跑另一个应用"。
2. **多镜像 AMP / 跨核 MICA**。每个核烧一个独立 ELF（每核一个 UniProton 镜像各带各的应用），或 MICA 下由 Linux 通过 remoteproc 把固件加载到 remote 核（09 篇）。"多个 ELF"以**每 ELF 独占（一）核**的方式成立——仍然不是 Linux 那种"单核多 ELF 由调度器分时"。

| 方案 | 多 ELF 的实现方式 | 与 Linux 跑 .out 的差别 |
|---|---|---|
| 单镜像多任务（主推） | 链接期把所有应用编进一个 ELF，各成一个 task 组 | 无运行期加载、无隔离、无独立 main |
| dlopen 动态模块 | 文件系统读 ELF 重定位加载，dlsym 调用 | 插件语义：无 main/无地址空间/无调度身份 |
| 多镜像 AMP / MICA | 每 ELF 独占一个核 | 以物理核代替进程隔离，核间靠 rpmsg |

**Q2-b：Linux 应用移植过来，是不是基本要重写？**

精确说：**业务逻辑不重写，"程序骨架"（进程模型）必须重写**。移植的本质是把**进程模型翻译成任务模型**——不是逐行翻译代码。

骨架层（要重写的部分）及对应关系：

| Linux 程序骨架 | UniProton 对应物 |
|---|---|
| `main()` 即应用入口 | `main` 退化为装配器：创建全部 task + 建好 IPC 后永久退场（4.2 节） |
| 一个进程 = 一个独立 .out | 一个 task（`TskInitParam`：taskEntry/prio/stackSize，Q1-b） |
| 进程间管道/socket | PRT 队列/信号量/事件，或同地址空间直接读写共享内存 |
| 阻塞 I/O（read 阻塞睡眠） | 信号量 Pend 阻塞，或 demo 式轮询 `while(cond) PRT_TaskDelay(...)` |
| fork/exec 子进程 | 链接期编成 task；确需运行期扩展才用 dlopen 插件 |
| 动态加载 .so、插件目录 | `OS_OPTION_DYNAMIC_MODULE` 的 dlopen（前提见上） |

业务层（可复用的部分）分三档：

| 档 | 内容 | 移植工作量 |
|---|---|---|
| 纯计算/协议库 | json/压缩/编解码/状态机/协议栈核心 | **几乎零改**，直接编入镜像 |
| POSIX 子集依赖 | pthread/malloc/printf/socket | litelibc + lwip 对应（lwip 提供 BSD socket API，改动小）；pthread 直调内核任务 |
| 重度 Linux 服务 | systemd/D-Bus/epoll 大规模 IO/动态插件体系/文件系统重度依赖 | **架构级重写**——这些 OS 服务本身在 UniProton 不存在 |

一个最小示意——Linux 三个进程经管道串行：

```
Linux:   producer.out ──pipe──► filter.out ──pipe──► consumer.out   （3 个 ELF，MMU 隔离）
UniProton:  main() { 建队列×2; 创建 task×3; }  （1 个 ELF）
            producerTask ──PRT_QueueWrite──► filterTask ──PRT_QueueWrite──► consumerTask
```

三个业务函数体（produce/filter/consume 的循环体）基本原样搬过来；变的是外面的壳——进程换成 task、管道换成队列、"操作系统帮我阻塞"换成"我自己 Pend/Delay"。

结论：**"基本重写"言过其实，"零改移植"也不成立**。经验比例大致是：业务函数体（占代码量大头）复用；每个应用重写一个 main→taskEntry 的壳（几十行）；跨应用通信按上表重接；重度依赖 Linux 系统服务的部分（如果有）才是真正的工作量所在。移植前先审计应用落在哪一档，比动手改代码更优先。

### Q3：写一个 UniProton 多任务 + 核间通信的最小 demo（发送 "Hello Uniproton"，多核接收打印）

**前提事实**（全部实测）：hi3093 参考配置**已启用 SMP**（`build/uniproton_config/config_armv8_hi3093/defconfig:34 CONFIG_OS_OPTION_SMP=y`）。SMP 下 UniProton 是**每核局部就绪队列** `g_runQueue[OS_MAX_CORE_NUM]`（prt_sched.c:21）+ 自旋锁，任务**粘创建者核**（机制详见下方 Q3 补充），无自动负载均衡。"核间通信"因此不需要额外机制：所有核共享同一地址空间，**PRT 队列本质就是一块共享内存环形缓冲 + 内核自旋锁保护**，`PRT_QueueWrite/Read` 天然跨核。

**demo 设计**：1 个队列 + 3 个任务（2 接收 1 发送）。发送任务往队列写 3 条 `Hello Uniproton`（消息体自带发送者句柄）；两个接收任务 `OS_QUEUE_WAIT_FOREVER` 阻塞等消息，醒来后打印"我在哪个核、我是哪个任务、消息来自谁"。全部代码只有 3 个函数：

```c
/* smp_demo.c —— UniProton 多任务 + 共享内存队列 demo（hi3093, SMP）
 * 编译接入：放入 demos/hi3093/apps/，在 PRT_AppInit 中调用 app_demo_init()
 * 构建：cd demos/hi3093/build && sh build_app.sh
 */
#include "prt_module.h"                 /* PRT_* API 汇总头（demo 惯例） */

#define Q_LEN     4                     /* 队列深度：4 个消息槽 */
#define Q_MSGSZ   64                    /* 每槽字节数 */
static U32 g_qid;                       /* 队列 ID：一块共享内存环形缓冲的句柄 */

/* 接收任务 ×2：阻塞等消息（等待期间切出 CPU，其他任务/空转核不受影响） */
static void receiver_entry(void)
{
    char msg[Q_MSGSZ];
    U32 len, self = 0, core = OsGetCoreID();          /* OsGetCoreID：读当前核号（os_cpu_armv8.h:102 内联） */
    (void)PRT_TaskSelf(&self);                        /* 我的任务句柄（prt_task.h:1321） */
    for (;;) {
        if (PRT_QueueRead(g_qid, msg, &len,
                          OS_QUEUE_WAIT_FOREVER) != OS_OK)   /* ★阻塞点：无消息→本任务挂起 */
            continue;
        printf("[core %u][recv task %u] got: %s\n", core, self, msg);
    }
}

/* 发送任务：写 3 条消息后退出 */
static void sender_entry(void)
{
    char msg[Q_MSGSZ];
    U32 self = 0;
    (void)PRT_TaskSelf(&self);
    for (int i = 1; i <= 3; i++) {
        int n = snprintf(msg, Q_MSGSZ,
                         "Hello Uniproton #%d (from task %u)", i, self);
        /* ★发送=写共享内存队列；内核自旋锁保护，跨核安全 */
        PRT_QueueWrite(g_qid, msg, n + 1, OS_QUEUE_NO_WAIT, OS_QUEUE_NORMAL);
        PRT_TaskDelay(OS_TICK_PER_SECOND);   /* 隔 1s 发一条（hi3093 tick=1000Hz），让接收端轮替拿到消息 */
    }
}

/* 装配器：建队列 → 建 3 任务 → 返回（main 上下文随后被永久抛弃，见 4.2 节） */
U32 app_demo_init(void)
{
    struct TskInitParam p = {0};
    TskHandle h;

    PRT_QueueCreate(Q_LEN, Q_MSGSZ, &g_qid);          /* 队列：nodeNum×maxNodeSize 的共享内存 */

    p.taskEntry = (TskEntryFunc)receiver_entry;       /* 接收 A */
    p.taskPrio   = 20;  p.stackSize = 0x2000;  
    p.name = "recvA";
    PRT_TaskCreate(&h, &p);  PRT_TaskResume(h);       /* Create 后必须 Resume 才就绪（demo 惯例） */
    p.name = "recvB";                                 /* 接收 B（同优先级，与 A 轮替收消息） */
    PRT_TaskCreate(&h, &p);  PRT_TaskResume(h);

    p.taskEntry = (TskEntryFunc)sender_entry;         /* 发送者，低一档优先级 */
    p.taskPrio   = 21;  p.name = "sender";
    PRT_TaskCreate(&h, &p);  PRT_TaskResume(h);
    return OS_OK;
}
```

**API 形式速查**（全部为 `bl` 直调的 UAPI，无 syscall）：

| API | 签名（uapi 位置） | 本 demo 中的角色 |
|---|---|---|
| `PRT_QueueCreate` | `(nodeNum, maxNodeSize, *queueId)`（prt_queue.h:243） | 分配共享内存环形队列 |
| `PRT_QueueWrite` | `(queueId, buf, size, timeOut, prio)`（:297） | 发送；prio 取 `OS_QUEUE_NORMAL/URGENT`（:202-204），timeOut 取 `OS_QUEUE_NO_WAIT=0`/`OS_QUEUE_WAIT_FOREVER=0xFFFFFFFF`（:210/:215） |
| `PRT_QueueRead` | `(queueId, buf, *len, timeOut)`（:270） | 接收；`WAIT_FOREVER` 时无消息→任务挂起（Pend 链，[03 篇](03-调度决策机制.md)） |
| `PRT_TaskCreate/Resume` | （prt_task.h:1165/:1187） | 建任务 + 放就绪队列 |
| `PRT_TaskSelf` | `(*taskPid)`（:1321) | 取当前任务句柄 |
| `OsGetCoreID` | 内联（os_cpu_armv8.h:102） | 读当前核号（读 MPIDR） |

**流程框架**（与 Q1/Q2 呼应）：

```
main → OsConfigStart → PRT_AppInit → app_demo_init（装配：1 队列 + 3 任务）
   └→ OsFirstTimeSwitch 永不返回，调度器接管
sender(21)   ──QueueWrite──► [共享内存队列 g_qid] ──QueueRead──► recvA(20) / recvB(20)
   两个接收任务同优先级：消息到来按 Pend 挂序唤醒，谁先挂谁先收。
sender 发完 3 条后任务函数 return → OsTaskExit 自动回收（prt_task_init.c:164 统一入口的收尾）。
```

**Q3 补充：想让 3 个任务确定性地跑在不同核上，怎么办？**

先修正一个容易想当然的认知——**UniProton SMP 是"粘核"模型，不是 Linux 式自动负载均衡**。实测机制链：

1. **创建时落核**：`OsTskSMPTcbInit()`（prt_smp_task_internal.h:69）`TSK_CORE_SET(taskCB, OsGetHwThreadId())`——任务 coreID 初值 = **创建者所在核**；`coreAllowedMask = OS_ALLCORES_MASK`（:73，全核允许但只是"资格"）。
2. **入队粘核**：`OsTskReadyAddOnly()`（smp/prt_task.c:62）`GET_RUNQ(task->coreID)`——任务进 coreID 指定核的**局部**就绪队列，没有"挑最空核"的逻辑。
3. **唤醒不换核**：`OsReschedTask()`（prt_sched.c:56）`coreId = task->coreID; if (coreId != THIS_CORE()) OsSmpSendReschedule(coreId)`——唤醒只向任务属核发调度 IPI，任务不迁移。
4. pthread 同样粘核（pthread_create.c:154 `TSK_CORE_SET(tskCb, OsGetHwThreadId())`）。

因此 **Q3 demo 的三个任务默认全部落在主核**（都在主核的 `app_demo_init` 里创建），打印出的 core 号会相同——demo 里队列之所以能体现"共享内存 + 跨核能力"，是机制上的保证；要真正看到多核并行，需要主动分配。三条路：

**路 A：`OsTaskSetAffinity` 静态绑核（hi3093 已开此特性，最直接）**

```c
/* 开关已就位：config_armv8_hi3093/defconfig:93 CONFIG_OS_OPTION_TASK_AFFINITY_STATIC=y */
PRT_TaskCreate(&h, &p);  PRT_TaskResume(h);
OsTaskSetAffinity(h, 1UL << coreN);   /* 绑到 coreN：prt_smp_task.c:238 */
```

`OsTaskSetAffinity(taskPID, OS_CORE_MASK)`（src/core/kernel/task/smp/prt_smp_task.c:238）→ `OsTskBindSelf`（:135）：从旧核队列摘下 → `OsTskSetCoreAllowed`（coreAllowedMask 收窄、nrCoresAllowed=1）→ `TSK_CORE_SET` 换核。demo 里给 3 个任务分别绑 `1UL<<0/1/2` 即可看到 `[core 0/1/2]` 交替打印。**两个边界要清楚**：它是内部接口（声明在 internal 头，非 UAPI）；Kconfig help 原话（task/Kconfig:22-26）——"*when os init, can set task affinity; if os is running, can not set affinity, this feature now is used belong L2 hac*"，即官方定位是 init 期/混合关键性框架的静态分配，运行期随意改绑不在设计用途内。demo 教学无妨，产品化遵循边界。

**路 B：中断绑核 + 每核事件驱动（嵌入式常态，无需绑任务）**

hi3093 同时开了 `CONFIG_OS_OPTION_HWI_AFFINITY`（defconfig:69）：把不同外设中断绑到不同核，每个核的 ISR 唤醒/驱动自己的任务——任务虽然"生于"主核，但每核任务集合由各自的中断源喂事件，天然形成核间分工（核 0 跑协议、核 1 跑采样……）。这是 RTOS SMP 更常见的实际用法：**按中断源分核，而不是按任务分核**。

**路 C：AMP/多镜像（绝对确定性）**

每核烧一个独立镜像（或 MICA 下 Linux remoteproc 拉起 remote 核，[09 篇](09-MICA混合部署与核间通信.md)），核间通信退回 rpmsg/共享内存+IPI。哪核跑什么 100% 静态可知——确定性最强、灵活性最差。

**为什么 UniProton 不做自动负载均衡？**对照 Linux：CFS 在唤醒/空闲时主动搬任务（wake_balance/idle_balance），换来平均吞吐；代价是任务落核不可预测、迁移带 cache/TLB 代价——对最坏时延是噪声源。UniProton 选择**任务落核 = 创建者核、永不漂移**（除非显式 SetAffinity），行为完全可预测——这是"确定性优先"设计哲学在 SMP 维度的又一次落地，与 [03 篇](03-调度决策机制.md)位图 O(1) 调度是同一逻辑。

**Q3 补充二：taskA/taskB 分别绑到指定核 + sender 定向发送（改进版 demo）**

两个前置澄清：

1. **绑核时机**：`OsTaskSetAffinityCheck()`（prt_smp_task.c:207-230）只查 PID 合法/非 idle/已创建/mask 非零，**不查任务状态**——挂起态（Create 后未 Resume）可以直接绑。所以标准时序是 **Create → SetAffinity → Resume**：绑完才入队，任务第一次被调度就落在目标核，无二次迁移。
2. **队列不是广播**：一个队列挂多个 reader 是**竞争消费**——每条消息只被一个任务取走（谁先 Pend 谁先得）。原版 demo 里 recvA/recvB 是"抢消息"而不是"都收到"。想要**定向发送**，正解是**信箱模式：每个目标一个队列，选队列即选目标**——队列句柄本身就是地址。

改进版（利用 `TskInitParam.args[4]` 传队列 ID，receiver 一个函数复用——`TskEntryFunc` 是 4 参数签名 `void (*)(uintptr_t,...)`（prt_task.h:1026），`OsTskEntry` 直接把 `args[0..3]` 传给任务函数，prt_task_init.c:171）：

```c
static U32 g_qA, g_qB;                    /* 两个信箱：qA=核0 的 taskA，qB=核1 的 taskB */

/* 接收任务（复用函数；qid 由 args[0] 传入） */
static void receiver_entry(uintptr_t qid, uintptr_t a2, uintptr_t a3, uintptr_t a4)
{
    char msg[Q_MSGSZ];
    U32 len, self = 0, core = OsGetCoreID();
    (void)a2; (void)a3; (void)a4;
    (void)PRT_TaskSelf(&self);
    for (;;) {
        if (PRT_QueueRead(qid, msg, &len, OS_QUEUE_WAIT_FOREVER) != OS_OK)
            continue;
        printf("[core %u][task %u] got: %s\n", core, self, msg);
    }
}

U32 app_demo_init(void)
{
    struct TskInitParam p = {0};
    TskHandle hA, hB;

    PRT_QueueCreate(Q_LEN, Q_MSGSZ, &g_qA);
    PRT_QueueCreate(Q_LEN, Q_MSGSZ, &g_qB);

    p.taskEntry = (TskEntryFunc)receiver_entry;
    p.taskPrio   = 20;  p.stackSize = 0x2000;

    p.name = "taskA";  p.args[0] = g_qA;              /* taskA 的信箱是 qA */
    PRT_TaskCreate(&hA, &p);
    OsTaskSetAffinity(hA, 1UL << 0);                  /* ★绑定核 0 */
    PRT_TaskResume(hA);

    p.name = "taskB";  p.args[0] = g_qB;
    PRT_TaskCreate(&hB, &p);
    OsTaskSetAffinity(hB, 1UL << 1);                  /* ★绑定核 1 */
    PRT_TaskResume(hB);

    /* sender 同前版：优先级 21，在主核 */
    ...
}

/* sender 定向发送：写哪个队列 = 发给哪个核上的哪个任务 */
PRT_QueueWrite(g_qA, "hello A@core0", 16, OS_QUEUE_NO_WAIT, OS_QUEUE_NORMAL);
PRT_QueueWrite(g_qB, "hello B@core1", 16, OS_QUEUE_NO_WAIT, OS_QUEUE_NORMAL);
```

要点归纳：

- **"指定核" = `OsTaskSetAffinity(handle, 1UL<<coreN)`**，插在 Create 与 Resume 之间（prt_smp_task.c:238，hi3093 已开 `OS_OPTION_TASK_AFFINITY_STATIC`）；内部 `OsTskBindSelf`（:135）对未入队任务是安全 no-op 摘队 + 改 `coreID`。
- **"发到指定核的指定任务" = 信箱模式**：每目标一个队列，sender 按目标写对应 `queueId`。队列跨核没有代价差异——都是同一共享内存，内核自旋锁保护；"发到核 1"和"发到核 0"的唯一区别是唤醒时 `OsReschedTask` 向哪个核发 IPI（prt_sched.c:56，`coreId = task->coreID`）。
- **想要"广播"语义**（所有接收者都收到同一消息）：开 N 个队列各写一份，或换"共享缓冲 + 计数信号量广播唤醒"形态（09 篇 MICA"收铃只 SemPost"的变体）——UniProton 队列原生没有广播。
- **`OsGetHwThreadId()` 小注**：pthread 路径创建的线程也是这个参数签名（pthread_create.c:154 粘核），`args` 传参形态与 POSIX `pthread_create` 的单 `void*` arg 不同——移植时 4 参数正好可以映射 `args[0..3]`。

**Q3 补充三：再加一套"共享缓冲 + 信号量广播唤醒"（与定向队列并存的第二种核间通信形态）**

先给语义事实：`PRT_SemPost` **一次只唤醒一个**等待者——prt_sem.c 的 Post 实现注释原话"如果有任务阻塞在信号量上，就激活信号量阻塞队列上的**首个任务**"（`OsSemPendListGet` 取队首 + `OsTskScheduleFastPs` 快速切换），没有等待者才 `semCount++`。所以"广播唤醒"的写法是：**计数信号量初值 0，sender 每轮为每个接收者 Post 一次（2 个接收者就 Post 2 次）**——每次 Post 唤醒队首一个，N 次 Post 恰好人手一个令牌。

形态：一份全局共享缓冲 `g_box` + 写序号 `g_seq` + 一口"铃" `g_bell`。**数据走共享内存，信号量只当"到货通知"**——这就是 [09 篇](09-MICA混合部署与核间通信.md) MICA"收铃只 SemPost"的微缩版。完整源码如下（独立文件即可编译，结构与主 demo 同构：2 个接收任务绑核 0/1 + 1 个广播任务，共 3 个函数）：

```c
/* bell_demo.c —— UniProton 共享缓冲 + 信号量广播 demo（hi3093, SMP）
 * 编译接入：放入 demos/hi3093/apps/，在 PRT_AppInit 中调用 app_bell_demo_init()
 * 构建：cd demos/hi3093/build && sh build_app.sh
 * 与 smp_demo.c（队列版）互相独立，可单独运行
 */
#include "prt_module.h"                 /* PRT_* API 汇总头 */

#define BOX_SIZE  64
#define RECV_NUM  2                    /* 接收者数量：广播时 Post 的次数 = RECV_NUM */

static char      g_box[BOX_SIZE];      /* 共享缓冲：全局只有一份（对照队列版的 N 个槽位） */
static U32       g_seq;                /* 写序号：接收者据此识别第几条、是否跳号 */
static SemHandle g_bell;               /* 广播铃：计数信号量，初值 0 */

/* 广播接收任务 ×2：等铃 → 读共享缓冲（taskA 绑核 0，taskB 绑核 1） */
static void bell_recv_entry(uintptr_t a1, uintptr_t a2, uintptr_t a3, uintptr_t a4)
{
    U32 self = 0, core = OsGetCoreID();          /* OsGetCoreID：os_cpu_armv8.h:102 内联 */
    (void)a1; (void)a2; (void)a3; (void)a4;
    (void)PRT_TaskSelf(&self);                   /* prt_task.h:1321 */
    for (;;) {
        /* ★等铃：阻塞在信号量上。OS_WAIT_FOREVER=0xFFFFFFFF（prt_sem.h:197）；
         * 每次被一个令牌唤醒（Post 一次唤醒队首一个，见正文说明） */
        PRT_SemPend(g_bell, OS_WAIT_FOREVER);
        /* 走到这里说明 sender 刚广播过：共享数据可见性由内核同步原语（锁+屏障）保证 */
        printf("[core %u][task %u] bell seq=%u: %s\n", core, self, g_seq, g_box);
    }
}

/* 广播任务：写共享缓冲 → 打铃（每轮 RECV_NUM 次 Post = 一次广播） */
static void bell_sender_entry(uintptr_t a1, uintptr_t a2, uintptr_t a3, uintptr_t a4)
{
    U32 self = 0;
    int i;
    (void)a1; (void)a2; (void)a3; (void)a4;
    (void)PRT_TaskSelf(&self);
    for (i = 1; i <= 3; i++) {
        /* ① 先写数据——★顺序不能反：打铃后接收者立即醒来读，先打铃会读到旧值 */
        (void)snprintf(g_box, BOX_SIZE, "broadcast #%d from task %u", i, self);
        g_seq++;                                 /* ② 再递增序号（接收者据此看跳号） */
        PRT_SemPost(g_bell);                     /* ③ 打铃：Post 一次唤醒队首一个等待者 */
        PRT_SemPost(g_bell);                     /*    RECV_NUM=2 → Post 2 次 = 广播 */
        PRT_TaskDelay(OS_TICK_PER_SECOND);       /* ④ 节流：1s 一条（hi3093 tick=1000Hz），
                                                     给接收者留读取窗口，避免新消息覆盖旧消息 */
    }
    /* 广播 3 条后任务函数返回 → OsTaskExit 自动回收（prt_task_init.c:164） */
}

/* 装配器：建铃 → 建 2 个绑核接收任务 + 1 个广播任务 → 返回（main 上下文随后被抛弃） */
U32 app_bell_demo_init(void)
{
    struct TskInitParam p = {0};
    TskHandle h;

    PRT_SemCreate(0, &g_bell);                   /* 计数信号量，初值 0（prt_sem.h:290） */

    p.taskEntry = (TskEntryFunc)bell_recv_entry;
    p.taskPrio   = 20;  p.stackSize = 0x2000;

    p.name = "bellA";                            /* 接收 A：绑核 0 */
    PRT_TaskCreate(&h, &p);
    OsTaskSetAffinity(h, 1UL << 0);              /* 绑核（prt_smp_task.c:238，见 Q3 补充二） */
    PRT_TaskResume(h);

    p.name = "bellB";                            /* 接收 B：绑核 1 */
    PRT_TaskCreate(&h, &p);
    OsTaskSetAffinity(h, 1UL << 1);
    PRT_TaskResume(h);

    p.taskEntry = (TskEntryFunc)bell_sender_entry;
    p.taskPrio   = 21;  p.name = "bellSender";   /* 广播者：主核，低一档优先级 */
    PRT_TaskCreate(&h, &p);  PRT_TaskResume(h);
    return OS_OK;
}
```

预期输出（两核交替，每轮两个接收者都收到同一条）：

```
[core 0][task 5] bell seq=1: broadcast #1 from task 7
[core 1][task 6] bell seq=1: broadcast #1 from task 7
[core 0][task 5] bell seq=2: broadcast #2 from task 7
[core 1][task 6] bell seq=2: broadcast #2 from task 7
...
```

**与定向队列版的本质差异**（两种形态的选择依据）：

| 维度 | 定向队列（补充二） | 共享缓冲 + 信号量（补充三） |
|---|---|---|
| 缓冲 | N 个槽位，每消息一份 | **全局一份**，新到覆盖旧 |
| 消费语义 | 独占（一条消息一个读者） | **广播**（所有等待者读同一份） |
| 背压 | 队列满可阻塞/报错 | 无背压——慢的接收者直接跳号（靠 `g_seq` 识别丢了哪条） |
| 数据传递 | 拷贝进队列槽位 | 零拷贝（读者直接看共享内存） |
| 适用 | 点对点命令/数据流 | 一写多读的状态/事件通知（09 篇 MICA 收铃模式） |

三个使用注意（教学 demo 里已体现）：①**先写后打铃**，顺序反了接收者读旧值；②广播无背压，sender 要节流（demo 里 `PRT_TaskDelay` 一秒一条就是节流），慢接收者会跳号——用 `g_seq` 检测；③若接收者数量运行期变化，"Post N 次"要跟着 N 变——接收者数固定的场景才适合这个写法，动态场景换事件模块（`PRT_Event`）更合适。

**若想看"裸共享内存 + 事件通知"形态**（不用队列）：把队列换成一段全局缓冲 + `volatile` 计数，发送方写完后 `PRT_SemPost(g_sem)`，接收方 `PRT_SemPend(g_sem, WAIT_FOREVER)` 后读缓冲——信号量替代队列承担"到货通知"，缓冲本体就是共享内存。那是更接近 MICA/openamp 收铃模式的写法（见 [09 篇](09-MICA混合部署与核间通信.md)"收铃只 SemPost"），代价是同步逻辑自己负责（谁写谁清、防覆盖）。教学上先跑通队列版（内核替你管同步），再读 09 篇看裸形态。

**与 Linux 的对照收尾**：这个 demo 在 Linux 里等价于"两个 reader 线程 + 一个 writer 线程 + 一把 mutex + 一个 condvar"（或一个消息队列 fd）——但那里要有 pthread 创建、syscall 陷入、内核对象；这里全是同镜像内的函数调用，队列只是"内核替你加锁的共享内存"，任务挂起/唤醒就是本系列 03/07 篇拆过的那两条固定路径。
