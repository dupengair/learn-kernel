# 02 - 总纲：内核形态与启动流程（Linux 6.6 vs UniProton）

## 0. 本篇导读

**一句话结论**：Linux 是"单体内核 + 两态隔离 + 系统调用"的独立 ELF；UniProton 是"静态库内核 + 单态裸机 + 函数直调"的单一 ELF。后续所有篇章的差异（无陷入开销、无地址空间切换、无缺页）都由这个形态差异派生。

本篇回答三个问题：
1. "内核"这两个字在两边分别指什么实体？
2. 从上电到第一个用户执行体，两边各走什么路径？
3. 应用调一个 API，两边各经过什么环节？

## 1. 机制原理：形态为什么决定实时性

**API 路径长度 = 实时性的第一道门槛。**

- Linux 应用调用 `write()`：glibc 包装 → `ecall` 特权指令陷入 S 态 → 全量寄存器压栈（pt_regs，288 字节）→ 查 `sys_call_table[]` 间接跳转 → 进入/退出安全框架检查（ptrace/seccomp/audit/TIF 标志循环）→ `sret` 返回。每次调用固定承担这套开销。
- UniProton 应用调用 `PRT_TaskDelay()`：一条 `call` 指令。API 与应用同特权级（M 态）、同 ELF、同地址空间，**没有"进内核"这个动作**。

第二层含义是**加载与生命周期**：Linux 内核是独立 vmlinux，常驻内存、先于所有用户进程启动；UniProton 内核编译成 `.a` 静态库（`libRV64VIRT.a`），与应用目标文件链接进同一个镜像——"启动内核"和"启动程序"是同一件事。

第三层含义是 **ABI 形态**：Linux 系统调用号是稳定的 ABI（只能尾部追加），调用号本身是接口标识；UniProton 的 `PRT_*` 接口没有编号，只有函数签名，接口存在性由**链接期**决定（符号缺失即 `undefined reference`），运行期不存在"未实现的调用"。

## 2. 架构设计对比

```
Linux（两态）                          UniProton（单态）
┌─────────────────────────┐            ┌──────────────────────────────┐
│  用户态 (U)              │            │        单一 ELF @0x80000000    │
│  app + glibc             │            │  ┌────────────────────────┐  │
│    │ syscall(SYS_write)  │            │  │ app (main.c, console.c)│  │
│    ▼ ecall ──────────┐  │            │  ├────────────────────────┤  │
│ ═══════ 特权边界 ════│══│            │  │ litelibc (pthread 直调) │  │
│  内核态 (S)           ▼  │            │  ├────────────────────────┤  │
│  entry.S → sys_call_table│           │  │ UniProton 内核(静态库)    │  │
│  → __riscv_sys_write     │           │  │ sched/mem/irq/ipc...    │  │
│  独立 vmlinux，页表隔离   │           │  │ 同一 .text 段，无隔离     │  │
└─────────────────────────┘            │  └────────────────────────┘  │
                                       └──────────────────────────────┘
启动终点: exec /sbin/init               启动终点: OsFirstTimeSwitch 永不返回
```

## 3. 关键证据（数据结构 / 链接脚本）

**E1. Linux 系统调用分发表** — `openEuler-6.6/arch/riscv/kernel/syscall_table.c:19-22`

```c
void * const sys_call_table[__NR_syscalls] = {
	[0 ... __NR_syscalls - 1] = __riscv_sys_ni_syscall,   // 默认项=未实现
	#include <asm/unistd.h>                               // 宏展开逐项覆盖
};
```

- 调用号从 a7 寄存器取：`do_trap_ecall_u()` 读 `regs->a7`（`arch/riscv/kernel/traps.c:334`），查表间接调用（`arch/riscv/include/asm/syscall.h:82-94`）
- 未实现调用的兜底：`sys_ni_syscall()` 返回 `-ENOSYS`（`kernel/sys_ni.c:20-23`）
- 编号即 ABI 的证据：6.6 最新调用仍按序追加在尾部（`include/uapi/asm-generic/unistd.h:820-824`，`__NR_cachestat 451`、`__NR_fchmodat2 452`）；`arch/riscv/include/uapi/asm/unistd.h:37-40` 注释明言 riscv 专属调用号 "just in there for forwards compatibility"

> ⚠ openEuler 差异：`include/uapi/asm-generic/unistd.h` 在社区 6.6 基线（453 map_shadow_stack 封顶）之后继续尾部追加了 openEuler 自有调用号——`__NR_vstream_manage 454`（:829-830）、`__NR_kabi_reserved455~466`（KABI 预留槽，全部指向 `sys_ni_syscall`，:832-855）、`__NR_xsched_setattr/getattr 467/468`（openEuler 调度增强，:856-859），`__NR_syscalls` 由社区 6.6 的 454 扩到 469（:861-862）。追加方式仍是"只在尾部加号"，本身即是 ABI 只增不改策略的又一例证。

**E2. UniProton API：纯 C 函数声明，无调用号** — `UniProton/src/include/uapi/prt_task.h:1165`

```c
extern U32 PRT_TaskCreate(TskHandle *taskPid, struct TskInitParam *initParam);
```

**E3. 单一 ELF 的链接脚本** — `UniProton/demos/riscv64virt/build/rv64virt.ld:3-29`

```
MEMORY { IROM (rwx) : ORIGIN = 0x80000000, LENGTH = 0x04200000
         SRAM  ...  SYSSTACK ... }
ENTRY(_start)
.text : { *(.text .text.*) *(.rodata .rodata.*) ... } > IROM
```

`.text` 通配吞并所有目标文件的代码段——内核函数与应用函数落在**同一段**。注意：CLAUDE.md 早期提到的 `examples.ld` 实际不存在，该目录真实文件是 `rv64virt.ld`。

**E4. 静态库链接证据** — `UniProton/demos/riscv64virt/CMakeLists.txt:18,78-97,113-117`

- 编译选项 `-static -nostdlib -nostartfiles -ffreestanding`（裸机）
- `link_libraries(... libs/libRV64VIRT.a ...)` —— 内核以静态库参与链接
- `add_executable(${APP} $<TARGET_OBJECTS:bsp> ... $<TARGET_OBJECTS:app>)` —— bsp+config+app 合成一个可执行文件

**E5. pthread 适配 = 直调内核** — `UniProton/src/libc/litelibc/src/thread/pthread_create.c:166-231`

`__pthread_create` 内部直接调 `OsTaskCreateChkAndGetTcb()`、`OsTskContextInit()`、`PRT_TaskResume()`（:193/:207/:220）——pthread 与内核任务之间没有陷入边界，只是包了一层函数。（注意：`src/kal/` 目录在本仓库只有 IPC 适配，POSIX 线程适配实际位于 `src/libc/litelibc`。）

## 4. 启动路径走读

### 4.1 Linux：start_kernel 到第一个用户进程

| 步 | 函数 | 位置 | 要点 |
|---|---|---|---|
| 1 | `start_kernel()` | init/main.c:855 | C 入口，0 号进程上下文 |
| 2 | `setup_arch()` | init/main.c:878 | 早期初始化、DTB 解析 |
| 3 | `mm_core_init()` | init/main.c:913 | 建内存分配器（**6.6 已由 mm_init 改名**，旧资料勿用） |
| 4 | `sched_init()` | init/main.c:925 | 调度器初始化（中断未开） |
| 5 | `rest_init()` | init/main.c:665-712 | `user_mode_thread(kernel_init)` 诞**生 1 号进程**（:676）；`kernel_thread(kthreadd)` 诞生 2 号（:689）；0 号退化为 idle（:711） |
| 6 | `kernel_init()` | init/main.c:1417-1490 | 释放 initmem 后 `try_to_run_init_process("/sbin/init")`（:1482 起）**exec 第一个用户态进程**，失败则 panic |

此后每次 `write()` 都是一次完整陷入（详见 [07 篇](07-API路径与上下文切换开销.md)）。

### 4.2 UniProton：0x80000000 到第一个用户任务

| 步 | 函数 | 位置 | 要点 |
|---|---|---|---|
| 1 | `_start` | demos/riscv64virt/bsp/boot.s:1-12 | `la sp, sys_stackEnd; call main` |
| 2 | `main()` | demos/riscv64virt/apps/hello_world/main.c:95-98 | 仅一句 `return OsConfigStart();` |
| 3 | `OsHwInit()` | 同文件 :32-42 | 写 `mtvec`、开 MIE/MEIE/MSIE/MTIE（用户责任） |
| 4 | `OsConfigStart()` | demos/riscv64virt/config/prt_config.c:298-324 | `OsRegister() → OsInitialize() → OsStart()` |
| 5 | `g_moduleConfigTab[]` 扫描 | prt_config.c:207-238 | SYS/MEM/HWI/TSK/TICK…/**APP→PRT_AppInit**（:235），模块化注册-初始化 |
| 6 | `PRT_AppInit()` | main.c:66-93 | 创建第一个用户任务 "console thread"：优先级 25、栈 0x1000 |
| 7 | `OsActivate()` | src/core/kernel/task/amp/prt_task_init.c:139-159 | 创建 IdleTask（优先级 31 = LOWEST）→ `OsFirstTimeSwitch()` **永不返回** |
| 8 | `OsTskEntry()` | prt_task_init.c:164-185 | 所有任务统一入口：取 TCB → 调 `taskEntry` → `OsTaskExit` |

**关键洞察**：UniProton 的 `main()` 不是被调度的任务——它跑在一个"优先级 LOWEST+1 的伪任务"上下文里（`prt_amp_task_init.c:73`，比空闲任务还低），只负责把内核拉起来；`OsFirstTimeSwitch()`（`prt_sched_single.c:101-113`，注释 "never get here"）之后控制权永久交给调度器。对照 Linux：0 号进程退化 idle 后仍常驻调度——差别在于 Linux 需要 idle 兜底循环，UniProton 的 IdleTask 接过了这个角色。

## 5. 实现差异总结表

| 维度 | Linux 6.6（RISC-V, S 态） | UniProton（riscv64virt, M 态） |
|---|---|---|
| 内核形态 | 单体内核，独立 vmlinux | 静态库 libRV64VIRT.a + 应用合成单 ELF |
| API 路径 | glibc → ecall → sys_call_table → 内核函数 | 普通 call 指令直调 |
| API 标识 | 系统调用号（a7），ABI 稳定只增不改 | 函数符号，无编号 |
| 未实现 API | sys_ni_syscall → -ENOSYS（运行期） | 链接期 undefined reference |
| 入口/终点 | start_kernel → exec /sbin/init | _start → main → OsFirstTimeSwitch 永不返回 |
| 首个用户执行体 | init 进程（用户态） | "console thread" 任务（优先级 25） |
| 内存布局 | 内核/用户地址空间页表隔离 | IROM 0x80000000 单一映像，.text 不分内核/应用 |

## 6. 代码阅读指导

**推荐路线**（约 2 小时）：

1. `openEuler-6.6/init/main.c:855` start_kernel 骨架 → 665-712 rest_init → 1417-1490 kernel_init
2. `openEuler-6.6/arch/riscv/kernel/entry.S:295`（ecall 向量槽）→ `traps.c:331-359` → `syscall_table.c:19-22` → `kernel/sys_ni.c:20-23`
3. `UniProton/demos/riscv64virt/build/rv64virt.ld:3-29`（单 ELF 布局）
4. `UniProton/demos/riscv64virt/bsp/boot.s:1-12` → `apps/hello_world/main.c:95-98` → `config/prt_config.c:207-324`
5. `UniProton/src/core/kernel/task/amp/prt_task_init.c:97-159` → `prt_amp_task_init.c:73-110` → `prt_sched_single.c:101-113`
6. 对照阅读：`src/include/uapi/prt_task.h:1165` vs `src/libc/litelibc/src/thread/pthread_create.c:166-231`

**思考题**：

1. 若把 Linux `sys_call_table` 默认项从 `sys_ni_syscall` 改为 NULL + 运行期空指针检查，与现方案在 ABI 与安全上有何差异？UniProton 里等价的"接口不存在"在哪个构建阶段暴露？
2. UniProton 的 `main()` 跑在 LOWEST+1 伪任务上下文、首次切换后被永久抛弃；Linux 0 号进程却退化为常驻 idle。两者"引导上下文"归宿为何不同？
