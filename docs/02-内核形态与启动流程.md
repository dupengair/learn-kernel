# 02 - 总纲：内核形态与启动流程（Linux 6.6 vs UniProton）

## 0. 本篇导读

**一句话结论**：Linux 是"单体内核 + 两态隔离 + 系统调用"的独立 ELF；UniProton 是"静态库内核 + 单态裸机 + 函数直调"的单一 ELF。后续所有篇章的差异（无陷入开销、无地址空间切换、无缺页）都由这个形态差异派生。

本篇回答三个问题：
1. "内核"这两个字在两边分别指什么实体？
2. 从上电到第一个用户执行体，两边各走什么路径？
3. 应用调一个 API，两边各经过什么环节？

## 1. 机制原理：形态为什么决定实时性

**API 路径长度 = 实时性的第一道门槛。**

- Linux 应用调用 `write()`：glibc 包装 → `svc #0` 特权指令陷入 EL1 → `kernel_entry` 宏全量寄存器压栈（pt_regs，336 字节）→ 查 `sys_call_table[]` 间接跳转 → 进入/退出安全框架检查（ptrace/seccomp/audit/TIF 标志循环）→ `eret` 返回。每次调用固定承担这套开销。
- UniProton 应用调用 `PRT_TaskDelay()`：一条 `bl` 指令。API 与应用同特权级（EL1）、同 ELF、同地址空间，**没有"进内核"这个动作**。

第二层含义是**加载与生命周期**：Linux 内核是独立 vmlinux，常驻内存、先于所有用户进程启动；UniProton 内核编译成 `.a` 静态库（`libHI3093.a`），与应用目标文件链接进同一个镜像——"启动内核"和"启动程序"是同一件事。

第三层含义是 **ABI 形态**：Linux 系统调用号是稳定的 ABI（只能尾部追加），调用号本身是接口标识；UniProton 的 `PRT_*` 接口没有编号，只有函数签名，接口存在性由**链接期**决定（符号缺失即 `undefined reference`），运行期不存在"未实现的调用"。

## 2. 架构设计对比

```
Linux（两态）                          UniProton（单态）
┌─────────────────────────┐            ┌──────────────────────────────┐
│  用户态 (EL0)            │            │        单一 ELF @0x93000000   │
│  app + glibc             │            │  ┌────────────────────────┐  │
│    │ syscall(SYS_write)  │            │  │ app (openamp/main.c)   │  │
│    ▼ svc #0 ─────────┐  │            │  ├────────────────────────┤  │
│ ═══════ 特权边界 ════│══│            │  │ litelibc (pthread 直调) │  │
│  内核态 (EL1)         ▼  │            │  ├────────────────────────┤  │
│  vectors → el0_svc      │            │  │ UniProton 内核(静态库)   │  │
│  → sys_call_table       │            │  │ sched/mem/irq/ipc...    │  │
│  → __arm64_sys_write    │            │  │ 同一 .text 段，无隔离    │  │
│  独立 vmlinux，页表隔离  │            │  └────────────────────────┘  │
└─────────────────────────┘            └──────────────────────────────┘
启动终点: exec /sbin/init               启动终点: OsFirstTimeSwitch 永不返回
```

## 3. 关键证据（数据结构 / 链接脚本）

**E1. Linux 系统调用分发表** — `openEuler-6.6/arch/arm64/kernel/sys.c:58-61`

```c
const syscall_fn_t sys_call_table[__NR_syscalls] = {
	[0 ... __NR_syscalls - 1] = __arm64_sys_ni_syscall,   // 默认项=未实现（本体 sys.c:41-44）
#include <asm/unistd.h>                                  // 宏展开逐项覆盖（__SYSCALL 双宏 :51-56）
};
```

- 调用号从 x8 寄存器取：`do_el0_svc()` 读 `regs->regs[8]`（`arch/arm64/kernel/syscall.c:190`）；查表前先做 `scno < sc_nr` 上界检查，再经 `array_index_nospec()` 掩码索引（`syscall.c:49-52`），越界号不查表、直接 `do_ni_syscall()`（`syscall.c:22-34、54`）。表项签名统一为 `long (*)(const struct pt_regs *)`（`syscall_fn_t`），`SYSCALL_DEFINE` 生成的 `__arm64_sys_*` 包装从 pt_regs 拆参；`el0_svc_common()` 同时把号码回写 `regs->syscallno`（:82）供 ptrace 读取（`arch/arm64/include/asm/syscall.h:24-27`）
- 未实现调用的兜底：`sys_ni_syscall()` 返回 `-ENOSYS`（`kernel/sys_ni.c:20-23`）；arm64 表内默认项是其包装 `__arm64_sys_ni_syscall`（`arch/arm64/kernel/sys.c:41-44`）
- 编号即 ABI 的证据：6.6 最新调用仍按序追加在尾部（`include/uapi/asm-generic/unistd.h:820-824`，`__NR_cachestat 451`、`__NR_fchmodat2 452`）；`arch/arm64/include/uapi/asm/unistd.h:38` 直接 `#include <asm-generic/unistd.h>`——arm64 没有专属调用号表，编号完全复用 generic 序列，uapi 头只负责挑选 `__ARCH_WANT_*` 旧接口开关（:31-36）

> ⚠ openEuler 差异：`include/uapi/asm-generic/unistd.h` 在社区 6.6 基线（453 map_shadow_stack 封顶）之后继续尾部追加了 openEuler 自有调用号——`__NR_vstream_manage 454`（:829-830）、`__NR_kabi_reserved455~466`（KABI 预留槽，全部指向 `sys_ni_syscall`，:832-855）、`__NR_xsched_setattr/getattr 467/468`（openEuler 调度增强，:856-859），`__NR_syscalls` 由社区 6.6 的 454 扩到 469（:861-862）。追加方式仍是"只在尾部加号"，本身即是 ABI 只增不改策略的又一例证。

**E2. UniProton API：纯 C 函数声明，无调用号** — `UniProton/src/include/uapi/prt_task.h:1165`

```c
extern U32 PRT_TaskCreate(TskHandle *taskPid, struct TskInitParam *initParam);
```

**E3. 单一 ELF 的链接脚本** — `UniProton/demos/hi3093/build/hi3093.ld:6-37`

```
MEMORY { IMU_SRAM (rwx) : ORIGIN = 0x93000000, LENGTH = 0x800000
         MMU_MEM  (rwx) : ORIGIN = 0x93800000, LENGTH = 0x800000 }
ENTRY(__text_start)
.text : { *(.text) *(.text.*) *(*.text) ... } > IMU_SRAM
```

`.text` 通配吞并所有目标文件的代码段——内核函数与应用函数落在**同一段**。ARM64 demo 额外开了 MMU（`bsp/mmu.c` 建 `g_mem_map_info[]` 页表），但所有映射区 `.virt == .phys` 恒等映射，仅用于区分内存属性（代码段 RX、外设 Device-nGnRnE），不做地址空间隔离——"单一地址空间"的形态在 A 核上不变；页表本身也放在镜像内（hi3093.ld 的 `.mmu.table.base` 段）。

**E4. 静态库链接证据** — `UniProton/demos/hi3093/CMakeLists.txt:19-20,62-70,121`

- 编译选项 `-march=armv8.2-a -nostdlib -nostdinc -nostartfiles`（裸机，:19-20）
- `link_libraries(... libs/libHI3093.a ...)`（:66）—— 内核以静态库参与链接，同链还有 libmetal.a/libopen_amp.a（:68-70）
- `add_executable(${APP} ${OBJS})`（:121 等各 APP 分支）—— bsp+config+app 的目标对象合成一个可执行文件

**E5. pthread 适配 = 直调内核** — `UniProton/src/libc/litelibc/src/thread/pthread_create.c:166-231`

`__pthread_create` 内部直接调 `OsTaskCreateChkAndGetTcb()`、`OsTskContextInit()`、`PRT_TaskResume()`（:193/:207/:220）——pthread 与内核任务之间没有陷入边界，只是包了一层函数。（注意：`src/kal/` 目录在本仓库只有 IPC 适配，POSIX 线程适配实际位于 `src/libc/litelibc`。）

## 4. 启动路径走读

### 4.1 Linux：start_kernel 到第一个用户进程

| 步 | 函数 | 位置 | 要点 |
|---|---|---|---|
| 1 | `start_kernel()` | init/main.c:855 | C 入口，0 号进程上下文 |
| 2 | `setup_arch()` | init/main.c:878 | 早期初始化、DTB 解析 |
| 3 | `mm_core_init()` | init/main.c:913 | 建内存分配器（**6.6 已由 mm_init 改名**，旧资料勿用） |
| 4 | `sched_init()` | init/main.c:925 | 调度器初始化（中断未开） |
| 5 | `rest_init()` | init/main.c:665-712 | `user_mode_thread(kernel_init)` 诞**生 1 号进程**（:676）；`kernel_thread(kthreadd)` 诞生 2 号（:689）；0 号退化为 idle（:711） |
| 6 | `kernel_init()` | init/main.c:1417-1490 | 释放 initmem 后 `try_to_run_init_process("/sbin/init")`（:1482 起）**exec 第一个用户态进程**，失败则 panic |

此后每次 `write()` 都是一次完整陷入（详见 [07 篇](07-API路径与上下文切换开销.md)）。

### 4.2 UniProton：0x93000000 到第一个用户任务

| 步 | 函数 | 位置 | 要点 |
|---|---|---|---|
| 1 | `OsElxState` | demos/hi3093/bsp/start.S:40-96 | 读 `CurrentEL` 判断启动异常级；EL2 起步则配 `HCR_EL2` 后 `ERET` 降级到 **EL1h**（:82-96） |
| 2 | `Start` | start.S:98-113 | 设 `sp = __os_sys_sp_end`（:107）、`BL mmu_init` 恒等映射（:110）、`B OsResetVector`（:113） |
| 3 | `OsResetVector` | src/arch/cpu/armv8/common/hwi/prt_reset_vector.S:40-43 | `LDR x0,=OsVectorTable; MSR VBAR_EL1,X0` 设异常向量基址；清寄存器/BSS 后 `BL main`（:155） |
| 4 | `main()` | demos/hi3093/apps/openamp/main.c:522-524 | 仅一句 `return OsConfigStart();` |
| 5 | `OsConfigStart()` | demos/hi3093/config/prt_config.c:501-528 | `OsHwInit()`（:512，空函数）→ `OsRegister()`（:515）→ `OsInitialize()`（:521）→ `OsStart()`（:527） |
| 6 | `g_moduleConfigTab[]` 扫描 | prt_config.c:255-305 | SYS/MEM/HWI/TSK/TICK…/**APP→PRT_AppInit**（:289），模块化注册-初始化 |
| 7 | `PRT_AppInit()` | main.c:437-496 | `RpmsgHwiInit()` 注册核间中断（:455）；`OsTestInit()` 创建第一个用户任务 "TestTask"：优先级 25、栈 0x3000 |
| 8 | `OsActivate()` | src/core/kernel/task/amp/prt_task_init.c:139-159 | 创建 IdleTask（优先级 31 = LOWEST）→ `OsFirstTimeSwitch()`（:156）**永不返回** |
| 9 | `OsTskEntry()` | prt_task_init.c:164-185 | 所有任务统一入口：取 TCB → 调 `taskEntry` → `OsTaskExit` |

**关键洞察**：UniProton 的 `main()` 不是被调度的任务——它跑在一个"优先级 LOWEST+1 的伪任务"上下文里（`prt_amp_task_init.c:73`，比空闲任务还低），只负责把内核拉起来；`OsFirstTimeSwitch()`（`prt_sched_single.c:101-113`，注释 "never get here"）之后控制权永久交给调度器。对照 Linux：0 号进程退化 idle 后仍常驻调度——差别在于 Linux 需要 idle 兜底循环，UniProton 的 IdleTask 接过了这个角色。ARM64 上另有两处与 riscv64virt 不同：异常向量基址由内核汇编 `OsResetVector` 写 `VBAR_EL1`（`prt_reset_vector.S:42-43`，不再是应用责任），且入口先从 EL2 降级到 EL1（`start.S:82-96`）——裸机 RTOS 也必须处理 AArch64 的异常级拓扑，但降级后全程单一 EL1，"单态"结论不变。

## 5. 实现差异总结表

| 维度 | Linux 6.6（ARM64, EL1） | UniProton（hi3093, EL1） |
|---|---|---|
| 内核形态 | 单体内核，独立 vmlinux | 静态库 libHI3093.a + 应用合成单 ELF |
| API 路径 | glibc → svc #0 → vectors/el0_svc → sys_call_table → 内核函数 | 普通 bl 指令直调 |
| API 标识 | 系统调用号（x8），ABI 稳定只增不改 | 函数符号，无编号 |
| 未实现 API | sys_ni_syscall → -ENOSYS（运行期） | 链接期 undefined reference |
| 入口/终点 | start_kernel → exec /sbin/init | OsElxState → OsResetVector → main → OsFirstTimeSwitch 永不返回 |
| 首个用户执行体 | init 进程（用户态 EL0） | "TestTask" 任务（优先级 25） |
| 内存布局 | 内核/用户地址空间页表隔离 | IMU_SRAM 0x93000000 单一映像（MMU 恒等映射仅管属性），.text 不分内核/应用 |

## 6. 代码阅读指导

**推荐路线**（约 2 小时）：

1. `openEuler-6.6/init/main.c:855` start_kernel 骨架 → 665-712 rest_init → 1417-1490 kernel_init
2. `openEuler-6.6/arch/arm64/kernel/entry.S:618-633`（vectors 与 EL0 sync 槽、`.align 11` 即 0x800 对齐）→ `entry-common.c:875-881`（ESR_ELx.EC=SVC64 二次分发 → el0_svc）→ `syscall.c:175-191`（do_el0_svc 取 x8）→ `sys.c:58-61`（sys_call_table）→ `kernel/sys_ni.c:20-23`
3. `UniProton/demos/hi3093/build/hi3093.ld:6-37`（单 ELF 布局）+ `bsp/mmu.c:26-58`（恒等映射）
4. `UniProton/demos/hi3093/bsp/start.S:40-113` → `src/arch/cpu/armv8/common/hwi/prt_reset_vector.S:40-155` → `apps/openamp/main.c:437-524` → `config/prt_config.c:255-528`
5. `UniProton/src/core/kernel/task/amp/prt_task_init.c:97-159` → `prt_amp_task_init.c:73-110` → `prt_sched_single.c:101-113`
6. 对照阅读：`src/include/uapi/prt_task.h:1165` vs `src/libc/litelibc/src/thread/pthread_create.c:166-231`

**思考题**：

1. 若把 Linux `sys_call_table` 默认项从 `sys_ni_syscall` 改为 NULL + 运行期空指针检查，与现方案在 ABI 与安全上有何差异？UniProton 里等价的"接口不存在"在哪个构建阶段暴露？
2. UniProton 的 `main()` 跑在 LOWEST+1 伪任务上下文、首次切换后被永久抛弃；Linux 0 号进程却退化为常驻 idle。两者"引导上下文"归宿为何不同？
