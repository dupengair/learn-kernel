# 00 - 学习路径与方法指导

> 本文档是整个学习项目的纲领：明确学习主线、阶段划分、每阶段的代码入口 / 实验 / 产出，以及针对个人背景的学习策略。后续各专题文档按此路径展开。

## 一、学习者画像与总体策略

**已有基础**：
- 熟悉内核应用编程：系统调用、进程/线程（fork/pthread）、信号量/互斥锁/共享内存等 IPC、调度优先级参数（nice、SCHED_FIFO）
- 初步的内核机制概念：中断、虚拟内存、上下文切换等

**策略：从"熟悉的接口"向下钻，用"对比"驱动理解**

| 策略 | 说明 |
| ---- | ---- |
| 接口向下钻 | 从自己调用过的系统调用（`sched_setscheduler`、`nanosleep`、`sem_wait`）作为入口读源码，起点不是一无所知 |
| 对比驱动 | 每个主题都"两边同读"：同一问题 Linux 怎么做、UniProton 怎么做、为什么不同 |
| 问题驱动 | 核心问题只有三个（见下节），所有阅读围绕它们展开，避免陷入源码细节的汪洋 |
| 实验验证 | 结论必须有实验支撑（用户态可观测实验 + QEMU + 基准测试），不接受"书上说的" |
| 输出倒逼输入 | 每个专题必须产出对比文档进 `docs/`，写不出来 = 没学懂 |

**三个核心问题**（学习全程反复回到它们）：

1. **Q1 调度**：一个任务何时被调度上 CPU？——通用内核的决策依据 vs RTOS 的决策依据，根本差异是什么？
2. **Q2 核间通信**：多核/多系统之间如何协作？通用方案与 RTOS 方案的取舍是什么？
3. **Q3 实时性**：RTOS 的确定性时延是用什么技术手段换来的？各自牺牲了什么？

## 二、学习路径总览

```
阶段0 热身(建立全景) ──► 阶段1 调度对比 ──► 阶段2 中断与时间 ──► 阶段3 核间通信 ──► 阶段4 实时性总结
     环境与全景图          Q1 核心主题          实时性的地基           Q2 核心主题          Q3 收口
```

- 阶段 1、2、3 是主体，**顺序不可颠倒**：中断/TICK 是调度器的时间基准，先懂阶段 2 才能真正读懂调度；核间通信依赖对调度的理解（如负载均衡、IPI 唤醒）。
- 每阶段建议 1~2 周，可按空余时间伸缩；"自检问题"全部能回答才算通过。

### 阶段 1：调度机制对比（核心主题 Q1，约 2 周）

**目标**：能完整回答"一个任务何时上 CPU"，画出两边调度决策流程图。

**步骤 1.1 Linux 任务模型与调度类框架**
- 代码：`include/linux/sched.h`（task_struct 调度相关字段）、`kernel/sched/core.c`（`schedule()`、`pick_next_task()`、`__schedule()` 抢占点）
- 理解调度类优先级：`stop > deadline > rt > fair > idle`，`pick_next_task` 从高到低扫描
- 实验：用户态创建 SCHED_OTHER / SCHED_RR / SCHED_DEADLINE 三种线程，观察相互抢占行为（`sched_deadline` 需 root + 设置 `sched_rt_runtime_us`）

**步骤 1.2 公平调度：EEVDF（注意：6.6 正是 EEVDF 替代 CFS 的版本）**
- 代码：`kernel/sched/fair.c`（`pick_eevdf`、`update_curr`、vruntime/lag/eligibility/virtual deadline 概念）
- 6.6 的 `fair.c` 已是 EEVDF 实现，网上大部分资料讲的是旧 CFS 启发式 —— **以源码为准**，这是本阶段最大的坑
- 理解：虚拟时间、权重（weight/nice）→ 时间片比例； Eligibility 判定与虚拟 deadline 决定"下一个跑谁"
- 产出：一图解释"nice 值如何影响 CPU 份额"

**步骤 1.3 实时调度类 rt.c**
- 代码：`kernel/sched/rt.c`（位图优先级队列 `rt_prio_array`、`sched_setscheduler` 的入口 `__sched_setscheduler`）
- 对比点预留：rt.c 的就绪队列结构与 UniProton 的就绪队列结构极其相似（位图 + 每优先级队列），先标记后对比

**步骤 1.4 UniProton 任务调度**
- 文档：`doc/design/task.md` → 代码：`src/core/kernel/task/`（用 codegraph 查 `PRT_TaskCreate`、`PRT_TaskResume`、调度入口）
- 理解：任务控制块结构、优先级定义、就绪队列组织、调度触发点（创建/删除/挂起/恢复/中断退出/TICK）
- 注意 UniProton **无时间片轮转还是同优先级 FIFO/RR**，以源码和 `prt_config.h` 配置为准

**步骤 1.5 对比总结（本阶段核心产出）**
- 对比维度表格：调度实体 / 就绪队列结构 / 选任务算法复杂度 / 抢占时机 / 上下文切换实现（两边汇编级切换代码对照）/ 时间片语义 / 优先级动态调整
- 回答 Q1：Linux 用权重+虚拟时间追求**吞吐与公平**（结果是单次时延不可预测）；UniProton 用严格优先级抢占追求**最坏时延可预测**（结果是低优先级可能饿死、无公平性保证）

**自检问题**：
- Linux 为什么不让 SCHED_FIFO 任务保证微秒级确定性响应？列出至少 4 个不确定性来源（关抢占区、锁、IRQ、页错误、负载均衡迁移……）
- UniProton 的 `PRT_TaskDelay` 和 Linux 的 `nanosleep` 底层路径差异？（TICK 精度、hrtimer vs 定时器链）
- 两边上下文切换各自保存/恢复了什么？为什么 RTOS 的切换路径更短？

### 阶段 2：中断与时间管理 —— 实时性的地基（约 1 周）

**目标**：理解中断路径如何决定最坏时延；TICK 如何驱动调度。

| 主题 | Linux | UniProton |
| ---- | ----- | --------- |
| 硬中断 | `kernel/irq/`， IRQ 上下文、`local_irq_disable` 使用点 | `src/arch/*/`（hwi 向量表、中断嵌套策略）、`doc/design/hwi.md` |
| 软延迟处理 | softirq / tasklet / workqueue（不确定性来源） | 软中断/定时器队列（确定性设计） |
| 时间基准 | `kernel/time/`（hrtimer 高精度、NOHZ/tickless、`CONFIG_NO_HZ_FULL`） | TICK 实现（`src/core/kernel/tim/`，以源码为准） |
| 实验 | `cyclictest` 测量本机调度时延（`sudo cyclictest -m -p95 -h 100`），看直方图；再跑一个压测负载对比最坏时延变化 | rhealstone 基准（`demos/riscv64virt/build/build_app.sh task-switch` 等，含任务切换/抢占/消息延迟五项） |

**自检问题**：
- cyclictest 的高最坏时延值，能对应到内核里的哪些代码区域？（可用 ftrace `irqsoff`/`preemptoff` tracer 定位）
- RTOS 为什么普遍要求 ISR 极短、底半部确定化？

### 阶段 3：核间通信对比（核心主题 Q2，约 2 周）

**目标**：理解 SMP 核间协作与异构多 OS 协作两种模型。

**步骤 3.1 Linux 核间机制**
- IPI：`kernel/smp.c`（`smp_call_function*`）、`arch/x86/kernel/smp.c`（IPI 向量分发）；调度器如何用 IPI 做唤醒/负载均衡（`ttwu_queue`、`can_migrate_task`）
- 实验：观察 `/proc/interrupts` 中 CAL（function call）、RES（reschedule）中断计数随负载变化

**步骤 3.2 Linux rpmsg / virtio 框架**
- 代码：`drivers/rpmsg/`、`drivers/virtio/`；理解 virtqueue 环形缓冲与 vring 通知机制 —— 这是与异构核通信的标准框架

**步骤 3.3 UniProton 核间通信与混合部署**
- 代码：grep/codegraph 查 `rpmsglite`（UniProton 侧适配）、`demos/` 中 rpmsglite 测试用例（见 `build_app.sh` 的 master/slave 参数）
- 文档：`UniProton/doc/qemu/`、README 中 mcs 混合部署仓库链接（MICA 框架：Linux 大核 + UniProton 实时核）
- 理解：共享内存 + vring 通知的轻量直连方案 vs Linux 标准框架的差异

**步骤 3.4 对比总结**
- 对比维度：抽象层次（标准框架 vs 轻量库）/ 依赖（设备树、virtio 驱动栈 vs 极小依赖）/ 时延（框架开销）/ 适用场景（通用生态 vs 专用实时通道）
- 回答 Q2：核间通信的"通用性"与"确定性"如何取舍

**自检问题**：
- `smp_call_function` 在目标核处于关中断状态时会怎样？这说明什么时延问题？
- rpmsg 的"一次消息传递"经过哪些内存拷贝？两边各拷贝几次？

### 阶段 4：实时性技术手段专题总结（Q3 收口，约 1 周）

把前三个阶段的发现收拢成最终报告，按"技术手段"逐项对比：

| 技术手段 | 通用内核（Linux 6.6） | RTOS（UniProton） |
| -------- | -------------------- | ----------------- |
| 调度模型 | EEVDF 公平 + RT 类兜底 | 严格优先级抢占 |
| 抢占粒度 | `PREEMPT_NONE/VOLUNTARY/PREEMPT` 可配（`PREEMPT_RT` 完整合入在 6.12，6.6 需 out-of-tree 补丁） | 内核全抢占、极短关中断区 |
| 内存 | 虚存 + 按需分页 → 页错误引入不确定时延 | 静态/分区内存（`src/mem/` FSC），无页错误 |
| 锁与优先级反转 | rt_mutex 优先级继承（futex PI）；自旋锁关抢占 | 信号量优先级继承模式（`doc/design/sem.md`） |
| 中断 | 中断可能线程化、softirq 不确定 | 短 ISR + 确定性底半部 |
| 时间管理 | hrtimer/tickless，精度高但路径长 | 固定 TICK，简单可预测 |
| 测量 | cyclictest / ftrace / bpftrace | rhealstone 基准 |

最终回答 Q3：**实时性 = 可预测性，不是"快"** —— RTOS 用牺牲通用性（公平调度、丰富生态、动态内存便利）换取最坏情况有界。

## 六、避坑提醒

1. **6.6 = EEVDF 元年**：社区教程/博客绝大多数讲旧 CFS，`vruntime 红黑树选左下节点`的叙述在 6.6 已不成立，一切以 `kernel/sched/fair.c` 源码为准
2. **PREEMPT_RT 版本陷阱**：6.6 主线只有 `CONFIG_PREEMPT`，完整 `PREEMPT_RT` 到 6.12 才合入主线，对比"通用内核实时化"话题时注意版本
3. **UniProton 文档先于源码**：`doc/design/` 的中文设计文档写得清楚，先读文档建立框架再进源码，效率高得多
4. **不要一次读太多**：`fair.c` / `core.c` 都是数千行文件，永远"带着问题读一个函数"，不要通读
5. **实验先行存疑**：对任何"结论"先在自己机器上用可观测手段验证一次，再写进文档
