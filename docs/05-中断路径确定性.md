## 0. 本篇导读

**一句话结论**：Linux 中断路径的时延不确定性集中在**底半部**——softirq 是"pending 位图 + 多类型循环 + budget 重启"模型（2ms×10 轮上限 + NET_RX 每轮 300 包预算，超限重新置位自己），线程化中断又要过完整调度器；UniProton 的中断路径是"数组直调"——一个中断号一个 hook，O(1) 分发、无循环、无 budget，TICK 长工作推迟到中断尾部统一做且执行期间主动开中断。前者的时长有界但**很大且不可静态预测**，后者的时长**由代码本身决定，可静态分析**。

**两个版本事实**（本 checkout 实测，勿被旧资料误导）：
1. **本仓库 UniProton 无 SWI/软中断模块**——全库 grep `PRT_Swi` 无内核命中，`src/core/kernel/` 下无 swi 目录。底半部由"软件定时器回调 + ISR 唤醒任务"模式替代。
2. ARM64 上 Linux 的 softirq 检查不在汇编里，而在 C 层 `irq_exit_rcu`（entry-common.c:649，位于 `__el1_irq` 内；与 [04 篇](04-内核抢占与关中断窗口.md)的抢占检查同一位置）。

## 1. 机制原理

中断到处理之间的总时延 = 关中断窗口 + 分发路径 + 底半部延迟。本篇聚焦后两者：

- **Linux 顶半部**（hardirq 上下文）：GIC v3 读 IAR 取号（`gic_read_iar`）→ 写 EOIR 完成 → irq_desc → flow handler → action 链调 handler。顶半部本身不长，但** irq 退出点会内联执行 softirq**——这才是大头：一次中断退出最多可跑 2ms×10 轮 softirq 循环 + NET_RX 300 包×2 jiffies，最坏几十毫秒级。后续中断（甚至更高优先级的）被这段延迟，这就是"中断路径不确定"的核心。
- **UniProton**：VBAR_EL1 向量表按异常类型硬件分流（IRQ 槽直入 `OsHwiDispatcher`）→ GIC 读 IAR（`ICC_IAR1_EL1`）单次取号 → `g_hwiForm[hwiNum].hook(arg)` 数组直调 → 写 EOIR（`ICC_EOIR1_EL1`）完成。无循环无预算；嵌套深度无固定上限，由 `OS_OPTION_HWI_NESTED` 配置决定（hi3093 实测未开启，ISR 执行期间 IRQ 保持屏蔽、天然不嵌套）。TICK 特殊：ISR 里只 `TICK_NO_RESPOND_CNT++`，真正扫描工作推迟到中断尾部且开中断执行。

## 3. 关键数据结构

**L1. `struct irqaction`** — openEuler-6.6 include/linux/interrupt.h:120-134：`handler`（primary）/`thread_fn`/`thread`/`next`（共享中断链）/`thread_flags`（IRQTF_RUNTHREAD）。

**L2. softirq 向量表与预算** — openEuler-6.6 kernel/softirq.c:59 `softirq_vec[NR_SOFTIRQS]`；net/core/dev.c:4598-4600 `netdev_budget = 300`、`netdev_budget_usecs = 2s/HZ`（HZ=250 即 8000μs）。

**U1. UniProton 向量表元素 `struct TagHwiHandleForm`** — src/core/kernel/irq/prt_irq_internal.h:93-102：

```c
struct TagHwiHandleForm {
    union {
        HwiProcFunc hook;                    // 正常中断：处理函数
        struct TagHwiHandleForm *form;       // 私有中断：指向私有 form 数组
    };
    HwiArg param;
};
```

`g_hwiForm[]`（prt_irq.c:28）就是全部分发机制——没有 flow handler 概念、没有 action 链（组合模式 `OS_HWI_MODE_COMBINE` 才走链，prt_irq.c:230-240）。

**U2. 嵌套控制** — armv8 **没有** riscv 版的 `INT_NEST_DEPTH 20` 显式上限（该宏与"超限丢弃"为 riscv64 独有）。armv8 机制是两层：`OS_INT_COUNT` 计数器（prt_irq_external.h:26-29；非 SMP 即 `g_intCount`，定义 prt_irq.c:41）记录深度；`OS_OPTION_HWI_NESTED` 条件编译的 `OsHwiNestedIntEnable/Disable`（prt_hwi_internal.h:23-47）决定 hook 执行期间是否开 IRQ——开启才允许更高优先级中断打入，未开启（hi3093 实测默认未定义）则为空实现，ISR 全程关 IRQ。深度上限实际只受系统栈余量约束，无软件计数丢弃路径。

## 4. 关键代码路径走读

### 4.1 Linux：softirq 主循环（不确定性的代码本体）

kernel/softirq.c:486-500 定义两个常量，:535-608 是核心：

> ⚠ openEuler 差异勘误（两库 diff 复核）：`handle_softirqs` 拆分并非 openEuler 特有——社区 6.6.159 同样是 `handle_softirqs`（softirq.c:535-608）+ `__do_softirq()` 薄包装（:610）。softirq.c 的真实 openEuler 差异是新增 `CONFIG_FAST_IRQ` 快速外部中断路径（`xint_enter_rcu`/`__xint_exit_rcu`），详见 [10 篇](10-社区6.6与openEuler6.6调度与核间通信差异.md)。本篇代码块与行号均为 openEuler-6.6 实测。

```c
#define MAX_SOFTIRQ_TIME  msecs_to_jiffies(2)    /* :499 */
#define MAX_SOFTIRQ_RESTART 10                   /* :500 */

pending = local_softirq_pending();               /* :552 位图 */
restart:
	set_softirq_pending(0);                      /* :560 先清位图再开中断 */
	local_irq_enable();
	while ((softirq_bit = ffs(pending))) {       /* :566 依序执行所有 pending */
		h += softirq_bit - 1;
		h->action(h);                            /* :578 单个 action 无内层限时！ */
		...
	}
	local_irq_disable();
	pending = local_softirq_pending();
	if (pending) {
		if (time_before(jiffies, end) && !need_resched() && --max_restart)
			goto restart;                        /* :599 整轮重来，≤10轮 */
		wakeup_softirqd();                       /* :601 交班 ksoftirqd */
	}
```

调用点：`irq_exit_rcu`（:651-676）在 hardirq 计数清零后 `if (!in_interrupt() && local_softirq_pending()) invoke_softirq()`——**中断退出点内联执行**。ksoftirqd（:984-1003）是普通 CFS 优先级线程——负载高时 softirq 进一步延后。

**NET_RX 的预算证据** — net/core/dev.c:6990-7052：单轮 budget=300 包 + time_limit≈2 jiffies，超限 `time_squeeze++` 后 `__raise_softirq_irqoff(NET_RX_SOFTIRQ)`（:7046）**重新置位自己**——没收完的包让下一轮 softirq 继续，层层叠加。

**线程化中断为什么仍不确定** — kernel/irq/handle.c:61-137 `__irq_wake_thread`：`wake_up_process(action->thread)`（:136）只把 irq/xx 线程放进运行队列；线程主体（manage.c:1295-1338）设为 SCHED_FIFO（:1305）但要等当前任务让出 CPU、与其他 RT 任务竞争——"过调度器"就意味着时延由系统状态决定。request_threaded_irq 的设计语义见 manage.c:2100-2141 的文档注释（primary 返回 IRQ_WAKE_THREAD 唤醒线程执行 thread_fn）。

### 4.2 UniProton：向量到 hook 的固定路径

**入口（向量表+汇编）** — prt_reset_vector.S:40-43 复位时把 `OsVectorTable` 写入 `VBAR_EL1`。向量表（prt_vector.S:126-177）16 槽（4 异常类型 × 4 SP/EL 模式，与 Linux arm64 vectors 同构）：同步异常槽经 `EXC_HANDLE vecId` 宏 `b OsExcDispatch`（:20）；IRQ 槽（VBAR+0x280，Current EL with SP_ELx）:148-150 直跳 `OsHwiDispatcher`（prt_dispatch.S:174）：保存通用寄存器 + `spsr_el1/elr_el1`（:182-187）→ `BL OsHwiDispatch`（:191，进 C 层）。**换系统栈移到了 C 层**：`OsHwiDispatch`（prt_hwi.c:182-193）判断 `!OS_INT_ACTIVE`（被打断的是任务）则先记录任务栈指针（:187），再经 `OsSetSysStackSP`（prt_dispatch.S:237-240，`MOV SP,X0` 后 `BL OsHwiDispatchHandle`）切到系统栈；嵌套时（已在系统栈）直接处理。正常路径一路走到中断尾部调度**不返回**，只有嵌套/tick 嵌套场景才从 :194 `b OsContextLoad` 恢复被打断现场（:232 `eret`）。

**中断分类（硬件向量分发，BSP 不再参与）** — armv8 上 riscv 版的 mcause if-else 分层消失：IRQ 与同步异常由向量表硬件分流（同步异常统一 `b OsExcDispatch`，prt_hw_exc.S:70 保存 esr/far/spsr/elr 并切系统栈后 `BL OsExcHandleEntry`，prt_exc_init.c:151，异常不返回、走钩子后 `PRT_SysReboot`）；时钟（PPI）与外设中断（SPI）同走 `OsHwiDispatchHandle` → `g_hwiForm[]`，靠 GIC INTID 区分。demo BSP 只负责两件事：GIC 初始化（demos/hi3093/bsp/hwi_init.c:350-371 `OsHwiInit`——GICv3 的重分发器/分发器/CPU 接口配置，`ICC_SRE_EL1`/`ICC_BPR1_EL1`/`ICC_IGRPEN1_EL1`/`ICC_PMR_EL1` 等；cpu_config.h:19 `OS_GIC_VER=3`）和定时器（bsp/timer.c）。ISR 约束与 riscv 版同理：`OsHwiDispatchHandle` 置 `OS_FLG_HWI_ACTIVE`（prt_hwi.c:144）标记"处于中断当中"，调度路径据此与任务区分——ISR 里不要调阻塞 uapi。

**外部中断执行** — `OsHwiDispatchHandle`（prt_hwi.c:130-177，运行在系统栈、IRQ 屏蔽下）：

```c
UNI_FLAG |= OS_FLG_HWI_ACTIVE;        // :144 标记中断态（调度器据此拒绝在中断中切任务）
OS_INT_COUNT++;                       // :145 嵌套计数（armv8 无 20 层上限检查）
OsFiqEnable();                        // :148 清 DAIF 的 F 位，FIQ 可及时响应
hwiNum = OsHwiNumGet();               // :150 读 ICC_IAR1_EL1 取号（os_cpu_armv8_external.h:284）
if (OS_HWI_CLEAR_CHECK(hwiNum) || OS_HWI_NUM_CHECK(hwiNum))
    goto OS_HWI_CONTINUE;             // :152 spurious(1023)/号段检查
OsHwiNestedIntEnable();               // :156 OS_OPTION_HWI_NESTED 开启才有实体（hi3093 为空）
OsHwiHookDispatcher(hwiNum);          // :157 → g_hwiForm[hwiNum].hook(arg) O(1)直调
OsHwiNestedIntDisable();              // :158
OsHwiClear(hwiNum);                   // :165 写 ICC_EOIR1_EL1 完成（GIC 版 complete）
OS_INT_COUNT--;                       // :166
if (OS_INT_COUNT > 0) return;         // :168 嵌套中：直接退回上层中断
OsHwiDispatchTail();                  // :176 最外层：tick 补投递 + 调度
```

与 riscv 版的两处不同：没有"嵌套>20 丢弃"（无 INT_NEST_DEPTH）；读号/完成从 PLIC MMIO 的 claim/complete 换成系统寄存器 `ICC_IAR1_EL1`/`ICC_EOIR1_EL1`。`OsHwiHookDispatcher`（prt_irq.c:139-152）→ `OsHwiHandleActive`（prt_irq_internal.h:173-187，`form->hook(arg)`）与 `g_hwiForm[]` 数组直调完全架构无关，与 riscv 版一致。

**TICK 的"记账-执行"分离** — 时钟 ISR 只 `TICK_NO_RESPOND_CNT++`（prt_tick.c:327-333）；中断尾部（核心层 `OsHwiDispatchTail`，prt_sched_single.c:118-147——armv8 把 riscv 版放在架构层 prt_port.c 的这段逻辑统一到了核心调度层）补做：

```c
if (TICK_NO_RESPOND_CNT > 0) {                        // :121
    if ((UNI_FLAG & OS_FLG_TICK_ACTIVE) != 0) return; // :122 tick 嵌套防重入
    UNI_FLAG |= OS_FLG_TICK_ACTIVE;                   // :129
    do {
        OsIntEnable();        // ★执行期间主动开中断，可被更高优先级中断打断 :132
        g_tickDispatcher();   // 固定路径：任务超时链扫描→cpup→用户hook→软件定时器 :134
        OsIntDisable();
        TICK_NO_RESPOND_CNT--;
    } while (TICK_NO_RESPOND_CNT > 0);                // :137
}
OsHwiEndCheckTimeSlice(...);                          // :143 RR 时间片
OsMainSchedule();                                     // :146 ★中断尾部即调度
```

`OsTickDispatcher`（prt_tick.c:95-129）路径固定、无 budget；延时链按到期序排序（[03 篇](03-调度决策机制.md) OsTaskScan），扫描到未到期即停。

**中断尾部即调度** — 设计文档 doc/design/task.md:43 原文："如果在中断中发生任务调度，那么将记录下切换标志位，在用户 ISR 退出后进行任务切换……中断退出后切换任务只需要恢复最高优先级任务上下文即可"。对照 Linux：中断唤醒任务后要经历 `irq_exit → 返回内核态/用户态 → TIF 检查 → schedule()` 的间接层；UniProton 在中断尾部 C 函数 `OsHwiDispatchTail` 末尾直接调 `OsMainSchedule`（prt_sched_single.c:146）→ `OsTskContextLoad`（prt_dispatch.S:202）恢复最高优先级任务上下文 `eret`——**ISR 退出即新任务开始**，唤醒到运行的路径是固定的。

### 4.3 "无 SWI 模块"的核实结论与底半部替代物

本 checkout 实测：无 `PRT_Swi*` 符号、无 swi 目录、无 swi.md 设计文档（官方其他版本有，此树未包含）。现存底半部模式：
1. **软件定时器回调**（prt_swtmr.c:172 `OsSwTmrScan`，在 tick 尾部上下文成批执行）
2. **ISR 置标志/唤醒 + 高优先级任务干活**（task.md 推荐模式）
3. **entry/exit hook**（armv8 prt_hwi.c:248-263 注册 `PRT_HwiAdd/DelEntryHook/ExitHook`；触发点在 prt_irq.c:147-151 的 `OS_MHOOK_ACTIVATE_PARA1`）

与 Linux softirq 的本质区别：**每个回调只执行一次、无 pending 位图、无 budget/restart 循环、无 ksoftirqd**——处理时长由回调本身决定，最坏时间可静态分析（数一下注册了几个定时器、延时链最长几个任务）。

## 5. 实现差异总结表

| 维度 | Linux 6.6（arm64，EL1） | UniProton（armv8/hi3093，EL1） |
|---|---|---|
| 中断号获取 | GIC v3 单次读 IAR（EOI 后仍有 pending 会再取一次 IRQ 异常；riscv PLIC 才是 claim 循环） | 单次读 IAR（ICC_IAR1_EL1） |
| 分发结构 | irq_desc + action 链 + flow handler | g_hwiForm[] 数组一中断一 hook |
| 顶半部长度约束 | 无硬性约束（驱动自律） | lock→hook→complete→unlock 固定路径 |
| 底半部模型 | softirq 位图循环+budget+移交线程；tasklet；线程化中断 | tick 尾部顺序扫描或唤醒任务，单次执行无循环 |
| 线程化/延后时延 | wake_up_process 过调度器，受负载影响 | ISR 退出即调度，eret 直达最高优先级任务 |
| 嵌套 | 一般不嵌 hardirq；softirq 可被打断 | EL1 取 IRQ 异常时 DAIF.I 自动置位默认不嵌套；OS_OPTION_HWI_NESTED 可选开（hi3093 未开）；tick 尾部受控开中断；无固定层数上限（riscv 版为 20 层超限丢弃） |
| 最坏时延来源 | softirq restart、NET_RX budget、ksoftirqd 被调度、irq 线程竞争、关抢占区 | 更高优先级中断、关中断区（常数时间）、tick 尾部扫描长度（可数）、ISR 内禁阻塞 |

**思考题**：

1. Linux `handle_softirqs` 已有 2ms 上限为何还需 MAX_SOFTIRQ_RESTART=10？（提示：softirq.c:489-492 注释——jiffies 可能停走，如 stop_machine。软时限依赖时钟本身，硬重启计数是兜底。）

3. UniProton 把 tick 长工作放在中断尾部且执行期间 `OsIntEnable()`：这与 Linux 在 irq_exit 内联跑 softirq 有何异同？开中断窗口对最坏中断时延意味着什么？
