# 05 - 技术点3：中断路径确定性（顶半部/底半部模型对比）

> 实时性代码对比系列。本系列：[02 形态](02-内核形态与启动流程.md) | [03 调度决策](03-调度决策机制.md) | [04 抢占与临界区](04-内核抢占与关中断窗口.md) | **05 中断路径** | [06 内存确定性](06-内存管理确定性.md) | [07 API路径与上下文切换](07-API路径与上下文切换开销.md) | [08 优先级继承](08-优先级继承.md) | [09 MICA核间通信](09-MICA混合部署与核间通信.md)

## 0. 本篇导读

**一句话结论**：Linux 中断路径的时延不确定性集中在**底半部**——softirq 是"pending 位图 + 多类型循环 + budget 重启"模型（2ms×10 轮上限 + NET_RX 每轮 300 包预算，超限重新置位自己），线程化中断又要过完整调度器；UniProton 的中断路径是"数组直调"——一个中断号一个 hook，O(1) 分发、无循环、无 budget，TICK 长工作推迟到中断尾部统一做且执行期间主动开中断。前者的时长有界但**很大且不可静态预测**，后者的时长**由代码本身决定，可静态分析**。

**两个版本事实**（本 checkout 实测，勿被旧资料误导）：
1. **本仓库 UniProton 无 SWI/软中断模块**——全库 grep `PRT_Swi` 无内核命中，`src/core/kernel/` 下无 swi 目录。底半部由"软件定时器回调 + ISR 唤醒任务"模式替代。
2. RISC-V 上 Linux 的 softirq 检查不在汇编里，而在 C 层 `irq_exit_rcu`（与 [04 篇](04-内核抢占与关中断窗口.md)的抢占检查同一位置）。

## 1. 机制原理

中断到处理之间的总时延 = 关中断窗口 + 分发路径 + 底半部延迟。本篇聚焦后两者：

- **Linux 顶半部**（hardirq 上下文）：PLIC claim 读号 → irq_desc → flow handler → action 链调 handler。顶半部本身不长，但** irq 退出点会内联执行 softirq**——这才是大头：一次中断退出最多可跑 2ms×10 轮 softirq 循环 + NET_RX 300 包×2 jiffies，最坏几十毫秒级。后续中断（甚至更高优先级的）被这段延迟，这就是"中断路径不确定"的核心。
- **UniProton**：trap 入口 → mcause if-else 分发 → PLIC claim 单次读号 → `g_hwiForm[irqNum].hook(arg)` 数组直调 → complete。无循环无预算；中断嵌套上限 20 层（超限丢弃，prt_hwi.c:178）。TICK 特殊：ISR 里只 `TICK_NO_RESPOND_CNT++`，真正扫描工作推迟到中断尾部且开中断执行。

## 2. 架构设计对比

```
Linux (RISC-V, S态)                          UniProton (RISC-V, M态)
stvec→handle_exception                       mtvec→trap (prt_hw.s:109)
  scause 最高位分流                            mcause 精确值 if-else:
  do_irq                                       7=时钟 3=软中断(IPI) 0xb=外部
   ├ irq_enter_rcu                            ├ 外部: hwi_handler (prt_hwi.s:5)
   ├ handle_arch_irq                           │   ├ PLIC claim 读号(O(1)单次)
   │   └ PLIC claim 循环读号                    │   └ OsHwiDispatchHandle
   │       └ irq_desc→flow handler                ├ PRT_HwiLock(关中断)
   │           └ action 链调 handler              ├ OsHwiHookDispatcher
   └ irq_exit_rcu                                 │    └ g_hwiForm[irqNum].hook(arg) ★数组直调
       └ !in_interrupt && pending?                ├ PRT_HwiClearPendingBit(complete)
           __do_softirq ← ★不确定大头             └ PRT_HwiRestore
           位图循环+budget+restart×10          OsHwiDispatchTail_rv64
       (超限交 ksoftirqd 线程)                    ├ tick 补投递(开中断执行)
                                                 │    └ OsTickDispatcher(固定路径)
   线程化中断: IRQ_WAKE_THREAD                    └ OsHwiEndCheckTimeSlice(RR)
     wake_up_process(irq/xx 线程)               OsMainSchedule ★中断尾部即调度
     → 过完整调度器 → 时延仍不定                  → 直接 mret 进新任务
```

## 3. 关键数据结构

**L1. `struct irqaction`** — linux include/linux/interrupt.h:118-132：`handler`（primary）/`thread_fn`/`thread`/`next`（共享中断链）/`thread_flags`（IRQTF_RUNTHREAD）。

**L2. softirq 向量表与预算** — linux kernel/softirq.c:59 `softirq_vec[NR_SOFTIRQS]`；net/core/dev.c:4566-4568 `netdev_budget = 300`、`netdev_budget_usecs = 2s/HZ`（HZ=250 即 8000μs）。

**U1. UniProton 向量表元素 `struct TagHwiHandleForm`** — src/core/kernel/irq/prt_irq_internal.h:93-102：

```c
struct TagHwiHandleForm {
    union {
        HwiProcFunc hook;                    // 正常中断：处理函数
        struct TagHwiHandleForm *form;       // 私有中断：指向私有 form 数组
    };
    HwiArg param;
};
```

`g_hwiForm[]`（prt_irq.c:28）就是全部分发机制——没有 flow handler 概念、没有 action 链（组合模式 `OS_HWI_MODE_COMBINE` 才走链，prt_irq.c:230-240）。

**U2. 嵌套上限** — src/arch/cpu/riscv64/common/hwi/prt_hwi_internal.h:18 `INT_NEST_DEPTH 20`。

## 4. 关键代码路径走读

### 4.1 Linux：softirq 主循环（不确定性的代码本体）

kernel/softirq.c:486-500 定义两个常量，:535-608 是核心：

```c
#define MAX_SOFTIRQ_TIME  msecs_to_jiffies(2)    /* :499 */
#define MAX_SOFTIRQ_RESTART 10                   /* :500 */

pending = local_softirq_pending();               /* :552 位图 */
restart:
	set_softirq_pending(0);                      /* :560 先清位图再开中断 */
	local_irq_enable();
	while ((softirq_bit = ffs(pending))) {       /* :566 依序执行所有 pending */
		h += softirq_bit - 1;
		h->action(h);                            /* :578 单个 action 无内层限时！ */
		...
	}
	local_irq_disable();
	pending = local_softirq_pending();
	if (pending) {
		if (time_before(jiffies, end) && !need_resched() && --max_restart)
			goto restart;                        /* :599 整轮重来，≤10轮 */
		wakeup_softirqd();                       /* :601 交班 ksoftirqd */
	}
```

调用点：`irq_exit_rcu`（:651-676）在 hardirq 计数清零后 `if (!in_interrupt() && local_softirq_pending()) invoke_softirq()`——**中断退出点内联执行**。ksoftirqd（:942-956）是普通 CFS 优先级线程——负载高时 softirq 进一步延后。

**NET_RX 的预算证据** — net/core/dev.c:6841-6903：单轮 budget=300 包 + time_limit≈2 jiffies，超限 `time_squeeze++` 后 `__raise_softirq_irqoff(NET_RX_SOFTIRQ)`（:6897）**重新置位自己**——没收完的包让下一轮 softirq 继续，层层叠加。

**线程化中断为什么仍不确定** — kernel/irq/handle.c:61-137 `__irq_wake_thread`：`wake_up_process(action->thread)`（:136）只把 irq/xx 线程放进运行队列；线程主体（manage.c:1298-1341）设为 SCHED_FIFO（:1308）但要等当前任务让出 CPU、与其他 RT 任务竞争——"过调度器"就意味着时延由系统状态决定。request_threaded_irq 的设计语义见 manage.c:2125-2147 的文档注释（primary 返回 IRQ_WAKE_THREAD 唤醒线程执行 thread_fn）。

### 4.2 UniProton：trap 到 hook 的固定路径

**入口（汇编）** — src/arch/cpu/riscv64/common/common/prt_hw.s:109-233：保存全部寄存器（非嵌套时换系统栈，:205-208）→ `intterupt_in`（g_intCount++）→ `trap_entry(mcause)`（C 分发）→ `OsHwiDispatchTail_rv64`（tick）→ `intterupt_out` → 非嵌套则 `call OsMainSchedule`（:232，调度后不返回）。

**mcause 分发（demo BSP 提供）** — demos/riscv64virt/bsp/misc_m/trap_handler.c:63-86：mcause==7 走 `hwi_timer_handler`，==3 走 IPI，==0xb 走 `hwi_handler`，其余 `OsExcDispatch()`。:62 的注释是 UniProton ISR 约束的直接表述：**"trap_entry 的硬件状态为 M 态、处于中断当中，在调用 uapi 时候需要慎重考虑"**（即 ISR 里不要调阻塞 API——`OsTskSchedule` 在 :90 也会拒绝在中断中切换）。

**外部中断执行** — prt_hwi.s:5-14 → prt_hwi.c:173-195：

```c
if (OS_INT_COUNT > INT_NEST_DEPTH) return;   // :178 嵌套>20 直接丢弃
intSave = PRT_HwiLock();
OsHwiHookDispatcher(hwiNum);                  // :189 → g_hwiForm[irqNum].hook(arg) O(1)直调
PRT_HwiClearPendingBit(hwiNum);               // :190 PLIC complete
PRT_HwiRestore(intSave);
```

**TICK 的"记账-执行"分离** — 时钟 ISR 只 `TICK_NO_RESPOND_CNT++`（prt_tick.c:325-332）；中断尾部（prt_port.c:133-160）统一补做：

```c
do {
    OsIntEnable();           // ★执行期间主动开中断，可被更高优先级中断打断
    g_tickDispatcher();      // 固定路径：任务超时链扫描→cpup→用户hook→软件定时器
    OsIntDisable();
    TICK_NO_RESPOND_CNT--;
} while (TICK_NO_RESPOND_CNT > 0);
```

`OsTickDispatcher`（prt_tick.c:95-129）路径固定、无 budget；延时链按到期序排序（[03 篇](03-调度决策机制.md) OsTaskScan），扫描到未到期即停。

**中断尾部即调度** — 设计文档 doc/design/task.md:43 原文："如果在中断中发生任务调度，那么将记录下切换标志位，在用户 ISR 退出后进行任务切换……中断退出后切换任务只需要恢复最高优先级任务上下文即可"。对照 Linux：中断唤醒任务后要经历 `irq_exit → 返回内核态/用户态 → TIF 检查 → schedule()` 的间接层；UniProton 在汇编尾部直接 `OsMainSchedule` 载入新任务上下文 mret——**ISR 退出即新任务开始**，唤醒到运行的路径是固定的。

### 4.3 "无 SWI 模块"的核实结论与底半部替代物

本 checkout 实测：无 `PRT_Swi*` 符号、无 swi 目录、无 swi.md 设计文档（官方其他版本有，此树未包含）。现存底半部模式：
1. **软件定时器回调**（prt_swtmr.c:172 `OsSwTmrScan`，在 tick 尾部上下文成批执行）
2. **ISR 置标志/唤醒 + 高优先级任务干活**（task.md 推荐模式）
3. **entry/exit hook**（prt_hwi.c:156-171）

与 Linux softirq 的本质区别：**每个回调只执行一次、无 pending 位图、无 budget/restart 循环、无 ksoftirqd**——处理时长由回调本身决定，最坏时间可静态分析（数一下注册了几个定时器、延时链最长几个任务）。

## 5. 实现差异总结表

| 维度 | Linux 6.6 (S态) | UniProton (M态) |
|---|---|---|
| 中断号获取 | PLIC claim 循环读（一次进出消化多个） | 单次 claim |
| 分发结构 | irq_desc + action 链 + flow handler | g_hwiForm[] 数组一中断一 hook |
| 顶半部长度约束 | 无硬性约束（驱动自律） | lock→hook→complete→unlock 固定路径 |
| 底半部模型 | softirq 位图循环+budget+移交线程；tasklet；线程化中断 | tick 尾部顺序扫描或唤醒任务，单次执行无循环 |
| 线程化/延后时延 | wake_up_process 过调度器，受负载影响 | ISR 退出即调度，mret 直达最高优先级任务 |
| 嵌套 | 一般不嵌 hardirq；softirq 可被打断 | M 态默认关 MIE 不嵌套；tick 尾部受控开中断嵌套，≤20 层 |
| 最坏时延来源 | softirq restart、NET_RX budget、ksoftirqd 被调度、irq 线程竞争、关抢占区 | 更高优先级中断、关中断区（常数时间）、tick 尾部扫描长度（可数）、ISR 内禁阻塞 |

**推荐路线**：

1. `linux-6.6.159/arch/riscv/kernel/entry.S:21-110`（入口 scause 分流）→ `traps.c:351-360`（do_irq）→ `drivers/irqchip/irq-sifive-plic.c:374-394`（claim 循环）

**实验建议**：Linux 侧用 ftrace 定位最坏中断时延：`echo irqsoff > /sys/kernel/debug/tracing/current_tracer` 后跑网络压测（iperf3），看 tracing_max_latency；对比空闲时的值。

**思考题**：

1. Linux `__do_softirq` 已有 2ms 上限为何还需 MAX_SOFTIRQ_RESTART=10？（提示：softirq.c:489-492 注释——jiffies 可能停走，如 stop_machine。软时限依赖时钟本身，硬重启计数是兜底。）
2. 同为"中断里做最少工作、长活留给任务"：Linux irq 线程与 UniProton "ISR 置标志 + 最高优先级任务"相比，从唤醒到执行的路径各经过哪些环节？为什么后者时延可静态界定？（handle.c:136 vs prt_sched_single.c:62-80。）
3. UniProton 把 tick 长工作放在中断尾部且执行期间 `OsIntEnable()`：这与 Linux 在 irq_exit 内联跑 softirq 有何异同？开中断窗口对最坏中断时延意味着什么？
